## 0. 结论摘要（TL;DR）

1. **静态门禁层可信，请求脚本层不可信**：`check_templates` / `check_migration_heads` / `check_properties` **原生即可 exit 0**；`route_inventory` 与 `check_db_bootstrap`（凡走 `_test_bootstrap.make_app()` 建临时库副本的脚本）**原生在受限沙箱不可运行**，必须加 `scripts/_sandbox_compat.py` 垫片（captain 已独立复跑确认，本评估亦实测，见 §2.4/§2.5/§6）。请求型脚本 `smoke_test` / `permission_matrix` 的 exit 1 **不是**断言失败，而是写 `../_*.json` 抛 `PermissionError`（§2.6/§2.7/§7 T-X4）。
2. **最大单点缺口：写操作端点零负向覆盖（已定量）**：271 条路由里**非 GET 方法级端点 155 个**（POST 123 + DELETE 20 + PUT 12），**唯一被 `functional_test` 用字面 URL 覆盖的只有 5 个**（`/tasks/add`、`/api/quality/tasks`、`/api/quality/templates`、`/production_orders/add`、`/search/quick`），**约 150 个写操作端点没有任何自动化断言**（captain 给的估算 12–15 条 vs 实测 5 条路径 / 5 个方法级端点，见 §4.2，属"比预估更差"）。t1 复核出的 5 个 P0 业务缺口**全部落在这一层，现有工具链一条都拦不住**。
3. **CI 没有任何测试门禁**：`Jenkinsfile` 的「代码质量检查」只 `py_compile main.py`、`py_compile config.py`（flake8 被注释），5 个静态门禁 + 3 个请求脚本 + pytest **逐项未接入**（探针 §D 全 False）；`.github/workflows/docker-deploy.yml` 只 build+push；`scripts/deploy.bat` 零测试步骤。且该 stage 把异常降级为 `UNSTABLE`（在 Jenkins 里等于不失败）→ 仍需人工纪律。
4. **`tests/` 是空壳**：0 个 `.py`（只有空目录 `static/js` 与 `__pycache__`），无 `pytest.ini`/`pyproject.toml`/`tox.ini`/`setup.cfg`/`conftest.py`；conda 环境 `wage`（Python 3.9.21）**未装 pytest**、`requirements.txt` 未声明任何测试依赖。**是否应引入 pytest：结论是"应引入，但不是前置条件"**（§9 给出取舍与两阶段落地方式）。
5. **三个"伪门禁"形态**（本评估核心发现）：`route_inventory.py` 与 `permission_matrix.py` 的 `return 0` **恒真**（报告型）；`smoke_test.py:186` / `permission_matrix.py:129` 写文件失败**污染 exit code**（污染型）；`permission_matrix` 报出的"无校验视图 5 个"是**有意的 `@login_required` 页面**（假阳性型，§2.7/§7 T-X3）。

**一句话给下游**：阶段一可把 4 个静态门禁当"真闸门"、把 3 个请求脚本当"复用探针而非闸门"；阶段二必须新建「非 GET 负向权限 + 写路径/业务规则 + 端到端夹具」三层，并把门禁接进 Jenkinsfile（用 `error` 而非 `UNSTABLE`），否则 P0 缺口在第 N 次复现时仍零拦截。

## 2. 逐工具评估

### 2.1 `check_templates.py` —— 模板语法 + 能力登记闭环

- **行为**：Jinja2 `env.parse` 全量模板（`:22-33`）+ AST 读 `app/permissions.py::CAPABILITIES`（`:36-44`）+ 正则收集模板 `can()/can_any()`（`:47-57`）与路由 `@require_capability()`（`:71-84`）+ 校验 `ROLE_LANDING_ENDPOINTS` 指向的视图函数存在（`:87-113`）。
- **实测（原生 exit 0）**：`parsed 87 files` / `44 declared / 40 used in templates / 44 used on routes` / `landing 5` / `RESULT: OK`。
- **挡得住**：模板语法错误；模板或路由引用未登记 capability（两侧漂移）；落地端点函数名写错。
- **挡不住**：
  - 只做**声明存在性**校验，不做**能力↔角色矩阵**校验（"admin 不该看到却能看到"看不见）；
  - `40 used / 44 declared` → **4 个僵尸能力**（只声明无人用），门禁不报；
  - 模板里 `url_for('main.不存在的端点')`（渲染时才 `BuildError`）**不检查**——这是模板层最容易漏的一类；
  - 动态拼接的能力名（`can(cap_var)`）不进覆盖统计。
- **可信度**：**高**（纯静态、不需数据库）。`ROUTE_FILES`（`:60-68`）硬编码 7 个模块；探针 §A/§B 证明它**覆盖了全部"有视图"的模块**（含 `equipment.py`/`purchase.py`），`sales_routes.py` 是 1 字节空文件、无视图 → **本项当前无实际漏扫**，但新增路由模块必须同步改这个元组。

### 2.2 `check_migration_heads.py` —— 迁移链单 head

- **行为**：用 alembic `ScriptDirectory` **直接读 `migrations/`**（`:26-34`），不 `create_app()`、不碰数据库；判据单 head → 0，0 个或 >1 个 → 1（`:36-40`）。
- **实测（原生 exit 0）**：`HEADS=['p1nonctarget']` / `head_count=1  revisions=35`。
- **挡得住**：迁移分叉、链断裂。
- **挡不住**：**迁移 vs 真实库的实际一致性**。本项目 schema 事实来源是 `db.create_all()` + `_ENSURED_COLUMNS` 启动自愈（31 张表不在迁移历史），"单 head"与"库结构正确"是两件事——最危险的漂移（模型加列、`_ENSURED_COLUMNS` 没登记、迁移也没写）本门禁静默。也不校验"写了但不在链上"的孤立修订（`walk_revisions()` 只走链）。
- **可信度**：**高**（纯静态、零副作用、最快；docstring 明确记录为什么不用 `flask db heads`：后者会先 `create_app()` → 启动自愈 → 误写真实库，2026-08-27 已发生过一次）。

### 2.3 `check_properties.py` —— `@property`/不存在列当列用

- **行为**：AST 解析 `app/models.py` 建类信息表（`assigned`/`methods`/`props`/`bases`，`:82-120`），再 AST 遍历 `app/` 下 `.py`，对 `类名.属性名` 报两类违规：A 类「该类 `@property` 被类级访问」、B 类「该类及其项目内基类都没有这个名字」（`:137-164`）。
- **实测（原生 exit 0）**：`已扫描 23 个文件，模型类 74 个` / `RESULT: OK`。
- **挡得住**：项目**复发 5 次**的那类静默错误（`Employee.status == 'active'` 恒假过滤、`RawMaterial.material_name.like(...)` 抛 `AttributeError` 被吞、`FinishedProduct.current_stock` 这类不存在的列）。
- **挡不住**（docstring 已声明的边界）：只认类级访问（`instance.property` 无法静态判定）；只解析 `app/models.py` 里的类（其他模块自定义类不在名单）；`getattr`/字符串拼列名绕过检查。它只保证"名字存在"，**不保证"这个列在库里真的存在"**（库列口径靠 `check_db_bootstrap` 与探针）。
- **可信度**：**高**（纯静态、不导入应用）。

### 2.4 `route_inventory.py` —— 路由清单 + 重复注册【沙箱受限】

- **行为**：`make_app()` 后遍历 `app.url_map`，按 `(method, path)` 聚合检测重复（`:12-21`），按"GET 无参 / GET 带参 / 非 GET"打印全量（`:23-37`）。
- **实测**：
  - **原生 → exit 1（受限沙箱不可运行）**：`shutil.copy2(ROOT / 'app.db', os.path.join(_TMPDIR, 'app.db'))` → `PermissionError: [Errno 13] Permission denied: 'C:\Users\…\Temp\dsh-*\wms_test_*\app.db'`（captain 独立复跑同结论，本评估亦复现）；
  - **加 shim → exit 0**：`total rules=271` / `duplicate (method,path) registrations=0` / `GET no-arg=104 GET with-arg=56 non-GET=110`。
- **挡得住**：端点重复注册（同 method+path 挂两个 endpoint，在 Flask 里表现为静默覆盖）。
- **挡不住**：**没有任何断言**，唯一返回是 `return 0`（`:38`，实测探针 §E8 抽取到的返回语句只有 `['0']`）→ 除环境错误外**天然不可能失败**；不校验"路由↔模板"闭环；不校验方法集合合理性。
- **可信度**：**口径权威**——它是"路由总数 271"与三分类数字的**唯一权威来源**（直接读 `url_map`），但需要能 `create_app()`，因此依赖临时库副本环境。

### 2.5 `check_db_bootstrap.py` —— 空库自举 / 幂等 / 整表无遗漏【沙箱受限】

- **行为**：把 `app.db` 拷成种子库（`:71`），在临时空库上 `create_app()` 三次（首次 `:78` / 再次 `:79` / 无种子 `:86`），断言：自举后有账号、`admin` 哈希长度 ∈ (102,162)、二次启动不重复导入、哈希不被改写、无种子库安全跳过（`:74-88`）；再绕过自举直接 `copy_sqlite_into()`（`:48-64`），断言"一行没拷进去"与"整张表被跳过"都不发生（`:90-95`）。
- **实测（shim 下 exit 0）**：`种子库账号数=64` / `首次 64，再次 64` / `无种子库时 0` / `直接拷贝 6712 行，跳过 0 张表` / `OK`（与 captain 复跑数字一致）。
- **挡得住**：这是**唯一**覆盖"老库升级路径"的门禁——拷贝顺序、列匹配、空库判定、幂等。docstring 记录了存在理由（`DATETIME` 列曾因裸 SQL 读成字符串让 24 张业务表全军覆没，而账号数断言照样通过，所以必须单独盯 `skipped`）。
- **挡不住 / 注意**：
  - **与库内行数口径差 1**：这里 6712 行 vs t1 库内 6713 行（`copy_sqlite_into` 少 1 行，脚本**不做源库↔副本交叉校验**）；
  - 只验证"表没被整张跳过"与"行数>0"，**不逐表比对行数**，部分行级丢失不会被发现；
  - `main()` **没有 `sys.exit(...)`**（`:101-102`），成功靠隐式 0、失败靠未捕获 `AssertionError`；
  - 沙箱内**必须**加 shim。

### 2.6 `smoke_test.py` —— 全角色 GET 冒烟

- **行为**：8 个 actor（anonymous + 7 角色，`:141`）对全部可达 GET 路由（带参用库里真实首个 ID 填充，`:84-103`）各发一次请求，记录状态码/重定向链（≤12 跳检测死循环，`:157-168`）/500 响应体，最后写 `../_smoke_results.json`（`:186-188`），返回 `1 if errors else 0`（`:190`）。
- **实测**：`[plan] 可测 GET 路由 148 条，跳过 9 条`；8 个 actor 各 148 条；异常汇总打印 **`无 5xx / 异常 / 重定向死循环`**；**exit 1**。
- **exit 1 的真因（机制级）**：

  ```
  File "...\scripts\smoke_test.py", line 186, in run
      with open('../_smoke_results.json', 'w', encoding='utf-8') as f:
  PermissionError: [Errno 13] Permission denied: '../_smoke_results.json'
  ```

  → **断言全通过，写结果文件被沙箱拒绝 → exit 1**。下游含义：**"smoke_test exit 1"不是缺陷信号**。
- **明细二次解读**：读 `_smoke_results.json` 复算 admin 的 148 条 → **首跳 200 = 144 / 302 = 4，终态 200 = 148，0 异常、0 死循环、0 个"302→非 200"**。即 7 角色 × 148 条 **全绿、零问题**——它只证明"没 500/没异常"，不证明"权限对/数据对"。
- **挡不住**：只打 GET（110 条非 GET 零覆盖）；不判对错（越权 200 不报警）；55 条 GET 带参里 **9 条永远跳过**（`PATH_MODEL` 缺前缀映射，探针 §E4 实测清单）：`/api/material_requisitions/<int:id>/issued-items`、`/equipment/<int:id>/layout`、`/heat_lots/<int:id>`、`/inventory_counts/<int:id>`、`/material_returns/<int:id>`、`/purchase_orders/<int:id>`、`/shipments/<int:id>`、`/stock/<kind>`、`/workpieces/<int:id>`——**恰好集中在 `equipment/purchase/shipping/stock` 四个模块**，与 §2.7 的守卫扫描盲区**重合**，形成"四模块双层盲区"；3 条写死 SKIP（`:13`）无跳过理由；单请求、无并发、无幂等复跑；明细无期望值 → 无法自动判定。
- **可信度**：**中**（覆盖面尚可、噪音低，但"全绿"没有信息量，exit code 不可用）。

### 2.7 `permission_matrix.py` —— 权限矩阵

- **行为**：对每个 GET 路由，8 个 actor `follow_redirects=True`，按「`'权限不足'` 文案 / 401 / 403 / 登录页特征 `name="username"`」（`:100-103`）分类；打印三段（①匿名可访问应为 0 ②所有登录角色都能访问 ③源码上无校验的视图，`:106-127`）；写 `../_permission_matrix.json`（`:129-130`）；**`return 0`**（`:132`）。
- **实测（本轮全文复核）**：
  - ① 匿名可访问 = **0**（打印 `无`）；
  - ② 所有登录角色可访问 = 6 条：`/ [main.index] guards=['inline_role_check']`、`/api/notifications/recent`、`/api/notifications/stats`、`/my_tasks`、`/notifications`、`/user_dashboard`（后 5 条 `guards=['NONE']`）；
  - ③ 源码无校验视图 = 同样 5 个：`api_notification_stats`、`api_recent_notifications`、`manage_notifications`、`my_tasks`、`user_dashboard`；
  - **exit 1**，原因与 `smoke_test` 同形：`:129` 写 `../_permission_matrix.json` 的 `PermissionError`。
- **可信度分档（关键判断）**：
  - ①「匿名可访问=0」**可信**（实测请求结论）——但**只覆盖 GET**：110 条非 GET 的匿名访问完全没测；
  - ②③ 是**提示而非判定**，且本轮明确为**假阳性**：这 5 个视图符合 `AGENTS.md`「新增路由默认加 `@require_capability`；确实所有角色都要用的，才只留 `@login_required`」的有意形态（我的任务 / 用户面板 / 通知列表及 API），`functional_test` 已反向验证 `/api/*` 匿名返回 401/JSON。→ **不应作为缺陷上报**，但脚本把假阳性与真缺陷混在同一段输出，极易被下游误读为 P0；
  - `guards` 是**启发式**（`:19-50`）：函数体只看前 25 行、装饰器向上收集遇空行即停、`denied` 依赖中文字符串文案 —— 文案一改判定即静默失效。
- **结构性问题（比假阳性更重要）**：
  1. **永不失败**：结尾 `return 0`（探针 §E8 抽取到 `permission_matrix.py` 的返回语句只有 `['0']`）——即便匿名可访问 50 条，exit 仍是 0。接进 CI 只会得到恒真绿灯；
  2. **守卫扫描漏 47 个视图**：`ROUTE_FILES`（`:16`）只有 3 个模块，探针 §B 实测未扫描 `equipment.py`(15) + `purchase.py`(20) + `shipping.py`(7) + `stock.py`(5) = **47**。

### 2.8 脚手架与兼容层（5 个脚本共用的"隐形基座"）

## 5. 环境与可重复性风险

1. **`mkdtemp` 陷阱（已复现，机制明确）**：在 `tempfile.gettempdir()`（`…\Temp\dsh-*`）下 `os.mkdir(path, 0o700)` → 目录可建但**写入被拒**；`os.mkdir(path, 0o777)` → 写入成功。`tempfile.mkdtemp()` 固定 0o700 → 凡走 `_test_bootstrap.make_app()` 的 5 个脚本（`route_inventory` / `check_db_bootstrap` / `functional_test` / `smoke_test` / `permission_matrix`）**原生全部不可运行**。→ 这**不是代码缺陷**，是环境限制；但必须写进 runbook 的"失败分类规则"（§6.5）。
2. **夹具不冻结**：`make_app()` 从**当前** `app.db` 拷副本（`_test_bootstrap.py:25`）→ 同一脚本在不同数据状态下结果不同（今天 64 账号 / 63 员工，明天变了，参数化取值也变）。
3. **时间硬编码**：见 §2.10（`functional_test.py:218/308/340`）。
4. **CSRF 全关**（`_test_bootstrap.py:36`）：155 个非 GET 端点中，21 处显式 `@csrf.exempt` 之外的端点，其 CSRF 防护**在测试中从未被验证**；反向地，若某处误做大面积豁免，测试也发现不了 → 阶段二 P1。

## 6. 沙箱垫片 `_sandbox_compat.py`：机制、风险与失败分类

### 6.1 它改写了什么（逐项对照 `scripts/_sandbox_compat.py`）

| # | 改写点 | 位置 | 具体行为 | 为什么需要 |
| --- | --- | --- | --- | --- |
| 1 | 覆盖 `tempfile.mkdtemp` | `:32-41` | 自建 `_relaxed_mkdtemp()`：`os.mkdir(path, 0o777)` 取代标准实现的 0o700 | 沙箱拒绝向 0o700 目录写入（实测）；0o777 可写 |
| 2 | 覆盖 `subprocess.run` | `:43-75` | 仅当 `capture_output=True`：把 stdout/stderr 重定向到 `.analysis-scratch/` 下的临时文件再读回，返回 `subprocess.CompletedProcess`；**其余关键字（`timeout`/`check`/`cwd` 等）原样透传**，非 `capture_output` 调用走原函数 | 沙箱禁止命名管道（子进程 pipe 捕获抛 `PermissionError`） |
| 3 | 运行方式 | `:77-85` | `chdir` 到目标脚本目录、`sys.path` 前插脚本目录与仓库根、`runpy.run_path(target, run_name='__main__')` | 让脚本的 `from _test_bootstrap import ...` 与 `../_*.json` 相对路径按"脚本自身相对"解析 |
| 4 | 参数传递 | `:80-81` | `sys.argv = [target] + 剩余参数` | 让被测脚本看到正常的 argv |

**没有改写的**：被测脚本的任何一行代码、任何断言、任何阈值、任何退出码语义（`sys.exit(run())` 的返回值全部原样透传），以及 `_test_bootstrap.make_app()` 的"URI 必须在副本上"这道闸。

### 6.2 是否存在"shim 掩盖真实失败"的风险？

**结论：风险低，但有两处必须知道**：

1. **不掩盖断言结果**：shim 只改环境层与输出通道。`functional_test` 的 109 条断言、`check_db_bootstrap` 的 6 组 `assert`，其判定逻辑与被测数据完全没动；实测 shim 下 `check_db_bootstrap` exit 0 与 captain 复跑一致、`functional_test` 109/0，而 `smoke_test`/`permission_matrix` 在 shim 下**照样 exit 1**（因为它们的失败原因不在 `mkdtemp`）——这本身就证明 shim 不是"一律放行"。
2. **它在两处放宽了 Python 的安全语义**（只影响沙箱内的临时目录，不影响仓库与生产）：
   - 放宽的 `mkdtemp` **绕过了 CPython 的 `_resetperms` 加固**（标准实现会把目录权限重置为 0o700），在**多用户/共享主机**上 `0o777` 的临时目录是可被他人读写的——本沙箱属单用户隔离环境，可接受；**不要在共享机器上把它用于持有真实数据副本的场景**。
   - `subprocess.run(capture_output=True)` 的"文件替代管道"会让**依赖真实管道语义**的行为略有差异（如 `stdin` 传递、基于管道 flush 的交互、超大输出），本仓库 5 个脚本均不使用 → 实际无影响。另有一个良性副作用：临时输出文件写在 `.analysis-scratch/`（已在 `.gitignore`，`:1-12` 附近有 `.analysis-scratch/` 条目），`finally` 里 `os.remove` 清理（`:67-72`）。
3. **剩余残余风险（建议写进 runbook）**：
   - 若 shim 自身失败（如 `.analysis-scratch` 不可写），会以 `PermissionError` 冒泡 → 表现为 exit 1，**与"测试失败"同形**；分类方法是看 traceback 是否落在 `_sandbox_compat.py`。
   - `chdir` 改变了 `../_*.json` 的落点（§2.9），**这不是掩盖失败，但会改变产物位置**，台账里必须记录 cwd。
   - `sys.path` 被前插两个目录，理论上可能让某个脚本"意外导入"到仓库根的模块而掩盖 `ModuleNotFoundError`；本仓库 5 个脚本的导入都显式且存在 → 当前无实例。

### 6.3 shim 的三个正当用途与一个禁止项

- **正当**：① 受限沙箱内跑通 5 个需要临时库副本的脚本；② 让 CI 与开发者机用同一条命令（无沙箱时前置无害，`_sandbox_compat.py:21` 的 docstring 已声明"无沙箱限制的环境无需本层"）；③ 给下游一个可复制的"环境前置条件"。
- **禁止**：**不得**把 shim 当成"修好脚本"的手段——`smoke_test`/`permission_matrix` 在 shim 下仍 exit 1 就是证据；要转正必须修写文件与返回值（§8 P0-2/P0-3）。

### 6.4 失败分类规则（建议 runbook 直接采用）

| 观察 | 分类 | 处置 |
| --- | --- | --- |
| traceback 落在 `shutil.copy2(...wms_test_*/app.db)` / `tempfile.mkdtemp` 且是 `PermissionError` | **环境失败** | 加 shim 重跑；不要把 exit 1 记为代码失败 |
| traceback 落在 `smoke_test.py:186` / `permission_matrix.py:129` 的 `open('../_*.json')` 且是 `PermissionError` | **环境失败（产物写入）** | 结果以 stdout 为准；同时记为"该脚本不得作为 CI 门禁"的证据 |
| 断言文本 / `RESULT: FAIL` / 非空 `errors` 列表 | **代码/数据失败** | 记为缺陷 |
| traceback 落在 `_sandbox_compat.py` 内 | **垫片失败** | 检查 `.analysis-scratch` 可写性；修复后重跑 |

## 9. 结论：是否应引入 pytest（captain 要求，且不作为既有前提）

**结论：应当引入，但它是"阶段二的可选加速器"，不是阶段一/阶段二任何工作的前置条件；在引入之前，报告的每条结论都必须能用现有脚本 + shim 复现。**

### 9.1 证据（为什么现在还不能假设有 pytest）

- 环境实测：`python -m pytest --version` → `No module named pytest`；`python -m pip list` 无 pytest/coverage/hypothesis/faker 等。
- `requirements.txt` 无任何测试依赖条目（captain 独立复核一致）。
- 仓库无 `pytest.ini`/`pyproject.toml`/`tox.ini`/`setup.cfg`/`conftest.py`；`tests/` 下 0 个 `.py`。
- CI 未安装 pytest（`Jenkinsfile` 只 `pip install -r requirements.txt`，其中不含 pytest）→ **即使写了 pytest 用例，也没有任何流水线会跑**。

### 9.2 引入的理由（现状的具体痛点）

| 现状痛点 | pytest 如何缓解 |
| --- | --- |
| `functional_test` 用模块级 `PASS/FAIL` + 顺序耦合（§2.10），一个函数的副作用污染后续 | fixture 隔离 + 独立用例；失败即定位到用例 |
| 3 个脚本共用一个 `check(name, ok)`，无参数化 | `@pytest.mark.parametrize` 可把 155 个非 GET 端点、方案路线自动展开 |
| 无 `conftest.py` 统一 app/client（现在每个脚本自己 `make_app()` + `ensure_role_users()`） | 统一 fixture：临时库副本、7 角色 client、CSRF 开关、真实库哈希守护 |
| 无覆盖率工具 | `pytest-cov` 可给出"哪些视图/服务函数从未被任何测试执行"的量化清单（正好补 §4 的盲区度量） |
| 无"新路由自动纳入"的机制 | 参数化 from `app.url_map` 可让新增路由自动进入负向矩阵（P0-4） |

### 9.3 引入的代价与前置条件（必须先满足，否则是负收益）

1. **依赖声明**：新增 `requirements-dev.txt`（`pytest`、`pytest-cov`，可选 `pytest-flask`），并明确它**不进生产镜像**（`Dockerfile`/Jenkins 的安装步骤要区分）。
2. **CI 接线**：`Jenkinsfile` 必须新增安装 dev 依赖 + 执行测试的 stage，并用 `error` 表达失败（当前用 `UNSTABLE` = 不失败）。
3. **沙箱适配**：① 临时库副本仍需 `_sandbox_compat` 那类放宽（或在 `conftest.py` 内实现等价逻辑 + 允许 `TMPDIR` 覆盖）；② pytest 自身在受限沙箱内的临时目录/`tmp_path` fixture 会踩同一个 0o700 问题——**这一点必须先验证**（本评估未验证，因为当前环境没有 pytest）。
4. **迁移成本可控**：`functional_test` 的 11 个函数可保留原样，先用 pytest 包一层（`pytest.main`/`subprocess` 包装）逐条迁移，**不要一次性重写**，以免在阶段一"只读 + 零改动"约束下引入风险。
5. **不得引入"绿色幻觉"**：新测试必须显式断言（含负向与业务规则），否则只是把"无测试"换成"有测试框架但同样全绿"。

### 9.4 两条可行路线（择一，由 t7/t8 定稿）

| 路线 | 做法 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| **A. 不引入 pytest（沿用脚本式）** | 继续用 `check(name, ok)` 模式，新增 `scripts/negative_matrix.py`、`scripts/business_rules_test.py`、`scripts/e2e_*.py`，统一 `exit code` 语义与产物路径 | 零新增依赖、沙箱行为已验证、与本仓库风格一致（`AGENTS.md` 的"必跑门禁"就是脚本式） | 无参数化/覆盖率、"新路由自动纳入"仍要手写 | **阶段二默认走 A**，先让门禁真正接进 CI 并能失败 |
| **B. 引入 pytest（推荐作为阶段三/后续）** | 按 §9.3 的四项前置条件落地，逐步迁移 | 参数化、fixture、覆盖率、生态成熟 | 依赖 + CI + 沙箱三处新变量，短期风险高于收益 | 待 P0-1~P0-4 完成、且验证过沙箱内 `tmp_path` 可用后再引入 |

**一句话**：**现有工作不要以"有 pytest"为前提**；引入 pytest 是"值得做、但排在 P0 修复与 CI 接线之后"的改进项（对应 §8 P1-7）。

## 10. CI/部署侧评估（工具链的"最后一公里"）

1. **Jenkinsfile（探针 §D 逐项实测全 False）**：
   - `stage('代码质量检查')` 只跑 `python -m py_compile main.py` 与 `config.py`；flake8 一行被注释；
   - **5 个静态门禁 + 3 个请求脚本 + pytest 全部未接入**；
   - 该 stage 用 `try/catch` 把异常降级为 `currentBuild.result = 'UNSTABLE'`——**UNSTABLE 在 Jenkins 里不阻断**，且后续 stage 不 `error`；
   - `stage('数据库迁移')` 用裸 `python -c "...flask_migrate.upgrade..."`：**未先设 `DATABASE_URL`**、也未走 `AGENTS.md` 明令的「启动自愈 + `flask db stamp p1nonctarget`」路径 → 与"已因未指向副本而误写真实 `app.db`"同类形态，属**部署侧高危**（本评估只报告，不改动）；
   - `stage('健康检查')` 只 `curl -f http://localhost:5000/`：`/` 是 `inline_role_check` 落地页，对匿名/任意角色都返回 200 → **健康检查不具实质验收力**；
   - 失败分支回滚只恢复 `app.db`，不回滚代码/模板。
2. **GitHub Actions**：`.github/workflows/docker-deploy.yml` 只 build + push（无测试、无门禁）。
3. **结论**：当前"门禁"是**人工纪律**而非自动化闸门。阶段一方案若要求"每次变更必跑 X"，必须在 t7 的 runbook 里同时给出"接进 Jenkinsfile 的具体 stage 片段 + 失败语义（用 `error`）"，否则落地率不可保证。
