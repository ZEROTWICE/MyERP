## 2. 分层模型

### 2.1 六层 + 一横切（总表）

| 层 | 名称 | 判定输入 | 载体（现有 / 待建） | 连库 | 判据**形态** | 现有资产 | 缺口 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **L0** | 静态契约层 | 源码/AST、迁移文件、模板文本、`metadata` | `check_templates` / `check_migration_heads` / `check_properties` / `route_inventory` / `check_db_bootstrap` | 否（`route_inventory` 仅建 app 不发请求；`check_db_bootstrap` 在系统 TEMP 建临时库自举） | **exit 0 + 计数逐项相等** | 5 项全 exit 0 | 4 项新闸门未建（T-A / T-B 静态 / T-C / T-H）；期望值散落文档、无集中登记 |
| **L1** | 数据与 schema 层 | `app.db` **副本**、`sqlite_master`、`metadata`、`_ENSURED_COLUMNS` | `_test_bootstrap.make_app/ensure_role_users/seed_fixtures`（现有）；**待建**：按域可选的夹具模块 + 表/列对拍脚本 | ✅（副本） | **隔离闸 + 幂等 + 集合相等 + SHA256 不变** | 副本隔离闸已证有效 | **49 张零行表的按域夹具**；schema 对拍的脚本化 |
| **L2** | 可达性与权限矩阵层 | `test_client` 请求（不落真网络） | `smoke_test.py`（148 GET × 8 身份）/ `permission_matrix.py`（GET 子集 × 8 身份） | ✅（副本） | **0 个 5xx/异常/重定向死循环；匿名可访问 = 0；无校验视图不新增** | 断言已全绿 | **exit code 不可信**（M0）；110 条非 GET **不在本层覆盖内**；56 条带参 GET 依赖 L1 夹具才能覆盖 |
| **L3** | 功能与业务断言层 | 副本 + 夹具 + `test_client` + 直接调 service 层 | `functional_test.py`（109 断言）+ **待建**：T-F（件数守恒）/ T-B（假开关双向差分）/ T-E（能力矩阵 A/B diff）/ T-H 注入用例 | ✅（副本） | **业务量等式 / 差分 / 集合相等**（不是状态码） | 109 断言 exit 0 可信 | **G-1…G-4 零运行级用例**；非 GET 端点约 95 条无自动化断言（§3.1） |
| **L4** | 业务链端到端层 | L1 夹具 + 多模块协作 + 台账核对 | **待建**：按链组织的 E2E 用例集（建议 `scripts/e2e_chains.py`） | ✅（副本） | **链路台账守恒 + 状态机合法 + 全程可追溯到 `global_sn`** | **0 资产** | 全部（7 条链、夹具、断言） |
| **L5** | 手工与人因验收层 | 人在真实/准真实环境操作 | 上位计划 §5 的 11 条手工步骤（5-1…5-11） | 视步骤 | **二值 checklist + 非作者执行一次** | 步骤已写、未执行 | 验收记录模板（t7 规范） |
| **E** | 证据与台账（**横切**） | 每条用例的运行产物 | 结果台账（新文件 / 编号） | — | **可被第三人用同一命令复现；不可复跑的必须标「需非沙箱环境」** | 仅 2 个根 JSON（且被沙箱拒写） | 见 §2.4 |

> **层间是「判据强度」的递进而非「重要性」的递进**：L0 通过**不能**代表任何运行级行为；L5 通过**不能**替代 L0–L4 的可复跑证据。

### 2.2 逐层定义、边界与禁止事项

#### L0 静态契约层

- **职责**：在不启动业务逻辑的前提下，把「结构事实」钉死，防止文档漂移与结构性回归。
- **五个既有闸门 + 期望值（必须逐项相等，不接受「差不多」）**：
  - `check_templates.py` → `87 / 44 / 40 / 44 / landing 5` + `RESULT: OK`
  - `check_migration_heads.py` → `head_count=1 / revisions=35 / HEADS=['p1nonctarget']`
  - `check_properties.py` → `已扫描 23 个文件，模型类 74 个` + `RESULT: OK`
  - `route_inventory.py` → `total rules=271 / duplicate=0 / 104 / 56 / 110`
  - `check_db_bootstrap.py` → `64 账号 / 6712 行 / 跳过 0 张表`
- **待建 4 项（均来自上位计划 §3.3 的门禁盲区）**：T-A（通知触发器调用点）、T-B 静态侧（配置种子 key vs 读取点，**必须带白名单**）、T-C（`is_archived` 谓词形态 + 白名单）、T-H（`check_properties` 语义盲区补规则 + 注入用例）。
- **架构建议（本层新增）**：把上述**期望值集中登记为一份 `scripts/_gate_expectations.py`**（纯数据：闸门名 → 期望输出正则/计数），使 (a) 期望值变更必须显式改一处；(b) T-G 的阴性自测可以直接注入「坏期望值」验证闸门真的会失败。**这是 L0 自己的可信前提**（对应上位计划 §5-6 的「故意改坏一条断言须非 0」）。
- **禁止**：用 L0 的任何一次 exit 0 去声明运行级行为（尤其 G-1…G-4——它们的坐标在 `mes_service.py`，`check_properties` 结构上不可见）。
- **通道**：5 项中前三项原生可跑；`route_inventory` / `check_db_bootstrap` **必须走 shim**（V-4 已证原生失败）。

#### L1 数据与 schema 层

- **职责**：提供**可信、隔离、可重复**的数据底座，并独立对拍「模型 ↔ 库 ↔ 迁移」三方一致性。
- **三条判据**：
  1. **隔离闸**：`make_app()` 的 `SQLALCHEMY_DATABASE_URI` 必须落在副本（`:41-45` 已有 `RuntimeError` 硬闸）——**这是所有 L2/L3/L4 用例的合法性前提**。
  2. **夹具幂等**：`seed_fixtures()` 用 `get_or_make` 语义，二次调用不新增行（现状成立）；扩展夹具后**必须保持该性质**，否则 L4 的台账守恒断言会被夹具自身污染。
  3. **三方对拍**：`metadata` 表数 74 == 库内 75 − `alembic_version`；`_ENSURED_COLUMNS` = **10 表 / 43 列**；31 张非迁移表**名单逐项相等**；真实库 SHA256 不变。
- **待建**：把 `seed_fixtures` 从「按模型零散补行」升级为**按域可选**：`seed_domain(app, domain)`，`domain ∈ {purchase, goods_receipt, shipping, equipment, heat_lot, workpiece, quality, notification, audit}`，并返回「域 → (模型, id)」映射供 L4 直接引用。**理由**：49 张零行表中，采购/到货/发货/设备/炉次/工件这几族是 L4 的硬前置（G-7）。
- **量纲**：本层的对象是 **75 表 / 74 模型 / 43 列 / 31 表 / 35 修订 / 49 零行表**；引用时不得与「271 路由」「44 能力」混用（t1 §8.5 的三量纲规则同样适用于本层）。

#### L2 可达性与权限矩阵层

- **职责**：证明「每一条 GET 路由在 8 种身份下都不会 5xx/异常/死循环」，以及「匿名可达 = 0」。
- **判据**：`smoke_test` 的 `无 5xx / 异常 / 重定向死循环`（0 问题）+ exit 0（**依赖 M0**）；`permission_matrix` 的「匿名可访问 = 无」「无校验视图 = 既有 5 个、不新增」。
- **已知覆盖天花板（必须写入任何覆盖率声明）**：
  - `smoke_test` 只走 **GET**（`smoke_test.py:120` 显式跳过非 GET）→ **110 条非 GET 端点不在本层覆盖内**；
  - 56 条带参 GET 需要 `resolve_url` 能从夹具里取到 id，**未解析的成功率直接取决于 L1 夹具**；
  - 271 条规则的**理论上限是 271 × 8 = 2168 次请求**，`permission_matrix` 实际只覆盖 GET 子集（口径以它自己的输出为准）。
- **软判据标注**：「无校验视图」是**启发式正则**结论（上位计划 N-15），只能用于「**不新增**」的回归判定，**不得**写成「这 5 个视图运行时真的没有校验」。

#### L3 功能与业务断言层

- **职责**：把「业务量」而不是「HTTP 状态码」作为判据，是**P0 缺口的归属层**。
- **判据形态**（本层的四条标准形态）：
  1. **守恒等式**（T-F）：`fg` 减少量 == 被阻断量 == NC 增加量；`pass` 场景三项变化均为 0。
  2. **双向差分**（T-B）：同一返工场景在配置 `false`/`true` 下**工资数字必须不同**；**阴性对照**：非返工场景两次必须相同。
  3. **A/B 矩阵 diff**（T-E）：权限收口前后「角色 × 端点」矩阵 diff 必须**全为有意收紧**，无新增无校验视图。
  4. **契约断言**：导出必须 `spreadsheet` Content-Type + 非零字节（既有资产已含 13 处导出/模板的样例）；导入必须行级容错（坏行只记「第 N 行」不整体 500）；`/api/quality/tasks/import` **不得落盘**、`import_products` 的 `mkdtemp` 目录必须被回收。
- **现有资产的确切覆盖面**：`functional_test.py` 109 断言，其中**写请求调用 21 处**，去重后覆盖约 **12–15 个非 GET 端点**（`/system_configs`、`/tasks/add`、`/tasks/<id>/update_status`、`/tasks/<id>` DELETE、`/production_orders/add`、`/material_requisitions/add|issue`、`/inventory_counts/add|start|record|complete`、`/search/quick` + 2 个导出 POST）。⇒ **110 条非 GET 中约 95 条无自动化断言**（精确清单交 t5/t6 枚举，本文件只给数量级与口径）。
- **禁止**：用 L3 的单次通过去断言 L4 的链路性质（跨模块状态机与台账守恒只在 L4 判）。

#### L4 业务链端到端层

- **职责**：跨 ≥2 个模块、以**台账守恒**为判据，覆盖 7 条主链（对象清单见 §3.5）。
- **判据**：每条链必须同时给出 ① 状态机迁移合法；② 台账件数/金额守恒且差值可解释；③ 全程可追溯到 `global_sn`；④ 断链处**显式登记为已知缺口**而不是跳过。
- **现状**：零资产。**这是本设计认定的最大结构性缺口**，也是「阶段一测试方案」与「批次4/5 验收」的公共前置。
- **纪律**：链用例必须只用 L1 夹具造数据（禁止依赖真库现状——49 张零行表已证明真库不可依赖）。

#### L5 手工与人因验收层

- **必须手工的对象**（上位计划 §3.5 已裁定，本文件沿用并收敛）：通知**是否真的到达人**、审批**待办是否漏单**、不合格处置页**业务人员是否看得懂/办得完**、工资数字与**财务口径**是否一致、菜单是否**同源**、迁移后**真实库零改动**、导出文件在**真实 Excel** 中可打开。
- **判据**：二值 checklist + **由非作者执行一次** + 留记录（上位计划 §5 的硬要求）。
- **边界**：凡「可由脚本判定」的（模板/权限/属性一致性、件数守恒、谓词可见性反转、迁移幂等、触发器调用点存在性、脚本 exit code）**一律下沉到 L0–L4**，不得以「手工看了一眼」替代。

### 2.3 归层判定规则（决策树）

给出一条待测点，按顺序问：

1. **能在不运行应用逻辑的前提下用 AST/文本/静态集合判定吗？** → **L0**。
   （例：能力是否登记、属性是否是列、是否单 head、模板是否用 `can()`。）
2. **判定需要 `metadata`/库表/迁移图/夹具数据，但不需要业务行为吗？** → **L1**。
   （例：表列对拍、夹具幂等、隔离闸、真实库 SHA256。）
3. **只需要「请求能返回、不 5xx、匿名不可达」吗？** → **L2**。
4. **需要断言业务量（件数/金额/状态机/契约字节）吗？** → **L3**。
5. **需要跨 ≥2 模块且以台账守恒为判据吗？** → **L4**。
6. **判定依赖人的理解（文案/可用性/是否送达）吗？** → **L5**。

**上移/下移规则（防「层级注水」）**：

- 若某 P0 缺口（G-1…G-4）的结论目前只到「源码级」，**其用例必须落到 L3 或 L4**；把它「补一条静态规则」放进 L0 属于**层级错配**（L0 结构上不可见）。
- 若某 L2 断言（状态码）被用来声明业务正确性（例：「`/quality/nonconformities` 返回 200 所以不合格处置是对的」），**必须上移**到 L3/L4。
- 若某 L5 手工步骤能写成脚本判据（例「根 JSON mtime 未变」），**必须下移**到 L0/L2。
- 同一条用例**只允许有一个归属层**（出现在多层即为重复计量）；`E` 层记录是横切，不计入层归属。

### 2.4 横切层 E：证据与台账

- **目的**：让每个结论可被第三人用**一条命令**复现，且能区分「不可复跑」与「未跑」。
- **每条用例必须落 12 个字段**：
  `id | 层 | 用途 | 命令（可整段粘贴） | 期望（含期望 exit code） | 实得 | exit code | 库 SHA256 前 | 库 SHA256 后 | 证据落点（新文件/编号） | 取证方 | 时间 | 置信度 | 结论`
- **硬规则**：
  1. 证据落点必须是**本轮新建文件**（沙箱禁止改写已存在文件，C-5）；报告文件名**带日期/批次编号**，禁止依赖仓库根的 `_smoke_results.json` / `_permission_matrix.json`（当前写入必失败）。
  2. 结论只能是 `pass` / `fail` / `blocked(原因)` 三态之一；`blocked` 必须写清「需非沙箱环境」或「依赖未实现」。
  3. 「断言输出全绿但 exit code 不可用」必须如实写成**该形态**，不得写成 pass（M0 成立前）。
  4. 每条结论必须带**取证方**（谁跑的），跨会话引用时不得把他人的实测写成自己的（t1/§3.1 已定此纪律）。

## 4. 通过判据

### 4.1 三态判定与置信度

| 判定 | 含义 | 必须附带 |
| --- | --- | --- |
| **pass** | 命令按期望退出、断言全绿、期望值逐项相等 | 命令 + exit code + 期望/实得 + 取证方 |
| **fail** | 任一期望不满足（含**阴性用例应当非 0 却为 0**） | 差异明细 + 最小复现命令 |
| **blocked** | 环境/依赖原因无法取得可信结论 | **原因分类**：`需非沙箱环境` / `依赖未实现` / `需业务拍板` + 替代证据（如有） |

置信度沿用 t1 三档（**实测** / **源码级** / **未实测**），并要求：**凡结论来自 L0，一律标「静态」；凡来自 L2，一律标「可达性」**——不得含混为「已测试」。

### 4.2 判据形态表（判据强度从弱到强）

| 形态 | 层 | 适用 | 强度与风险 |
| --- | --- | --- | --- |
| exit code + 计数相等 | L0 | 结构事实 | 强（前提：M0 成立）；**不证明运行时行为** |
| 集合相等 / 差集为 ∅ | L0/L1 | 能力、schema、表清单 | 强 |
| SHA256 / mtime 不变 | L1/E | 只读性、真库保护 | 强 |
| 0 个 5xx/异常/死循环 | L2 | 可达性 | 中：**只证明「没崩」，不证明「对」** |
| 匿名=0 / 无校验视图不新增 | L2 | 权限回归 | 中（**启发式，软判据**） |
| 守恒等式（件数/金额） | L3/L4 | P0 缺口 | 强（业务量级） |
| 双向差分 + 阴性对照 | L3 | 假开关类 | 强（唯一能证「开关真接线」的形态） |
| A/B 矩阵 diff 全为有意 | L3 | 权限收口 | 强 |
| 人工 checklist（非作者执行） | L5 | 人因 | 中：**不可复跑，必须留记录** |

### 4.3 元判据 M0：exit code 可信（**所有自动化判据的前置**）

**M0 的三条子判据（缺一不可）**：

| # | 子判据 | 期望 |
| --- | --- | --- |
| M0-a | 正常跑 → exit code | `smoke_test` / `permission_matrix` / `functional_test` **全 0** |
| M0-b | **故意改坏一条断言**再跑 | 对应脚本 exit code **必须非 0**（阴性用例） |
| M0-c | `--no-dump` 运行 | **不得写**仓库根 `_smoke_results.json` / `_permission_matrix.json`（mtime/SHA 不变） |

**当前状态**：M0-a 对 `smoke_test`/`permission_matrix` **不成立**（写盘 `PermissionError` 覆盖了正确的 `return 0/1`——本轮复核 `smoke_test.py:186-190`、`permission_matrix.py:129-132` 确认）；**三条脚本均无 `--no-dump`**。⇒ **M0 未成立**，L2 层结论当前只能作「断言输出」引用。

**为什么 M0 必须排第一**：L2/L3/L4 全部自动化用例的最终「通过/失败」都由脚本 exit code 承载；exit code 不可信时，**后续所有「全绿」都无法排除「写盘失败伪装的绿」**（G-5 定性为 P0 工程缺口）。

### 4.4 判据前置条件与「等价通道」纪律

1. 连库/建 app 的命令**统一走** `python -B scripts/_sandbox_compat.py <script>`（V-4/V-5 已证差异；t1 的「原生可跑」不可依赖）。
2. 需要写报告时，命令的**产出必须落到新文件**（含编号/日期）；**禁止**为绕过沙箱去改被测脚本的输出路径（上位计划 §3.1 明令）。
3. 与历史报告比对时用 **SHA256 相同**作为「重跑未改变结论」的证据（T1 已用此法）。
4. **禁止**把「收尾写盘失败」写成本次运行的代码回归；也**禁止**把「断言全绿」写成 pass（M0 未成立期间）。
5. 任何以 `blocked` 结束的用例，**不得**在下游被换算成 pass 或「大致通过」。

### 4.5 分层合取门禁（交付级通过判据）

| 门禁 | 内容 | 适用频率 |
| --- | --- | --- |

| **G-L3** | `functional_test` 0 失败 + 本批相关 P0 用例的守恒/差分全部成立 | 按批次（批次4/5/7/8 起为硬门禁） |
| **G-L4** | 相关业务链台账守恒 | 按里程碑（链②⑤⑥优先） |
| **G-L5** | 相关手工步骤由**非作者**执行并留记录 | 按里程碑 |

**合取规则**：`交付级通过 = G-L0 ∧ G-L1 ∧ G-L2 ∧ (本批 G-L3) ∧ (里程碑相关 G-L4/G-L5)`。任一为 `fail` 或 `blocked` 时，**不得声明批次通过**；`blocked` 必须在交付说明中保留原文（不得抹平）。
