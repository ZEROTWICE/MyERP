## 二、端到端主流程

### 阶段 0：主数据准备

```
客户档案【完整】 ─┐
产品 + BOM + 工艺路线【部分】 ─┼─→ 具备接单条件
工序与工价【完整】 ─┤
员工 + 工序分配规则【完整】 ─┘

供应商档案【缺失】 ──X 无法支撑采购
```

补齐要点：无工艺路线的产品禁止创建生产订单。本期不强制 BOM。

---

### 阶段 1：销售接单【部分】

```
新建销售订单 SalesOrder
  → 选客户、订单号、年月、订单来源
  → 添加订单行 SalesOrderItem（产品、数量、方向、多组规格字段）
  → 状态：pending → confirmed → in_production → completed / cancelled
```

- 端点：`GET/POST /sales_order/add`、`GET /sales_order/<id>`、`GET/POST /sales_order/<id>/edit`
- 权限：admin / manager / sales（但导航入口只有 admin 能看到）

断点与缺陷：

1. 状态全靠编辑表单手动改，**没有提交/审批工作流**，只有 `confirmed → in_production` 是创建生产订单时自动触发的。
2. `completed` 不会随生产完成自动回写，需人工改。
3. **新增订单行时不保存 `customer_address_id`**，必须再进编辑页才能写入收货地址。
4. 分批到货 `delivery_batches` 是订单行上的 JSON 计划字段，**不产生任何出库或发货动作**。

---

### 阶段 2：采购【整段缺失】

```
请购 → 询价 → 采购订单 → 供应商发货 → 到货检验 → 收货入库 → 对账付款
   X      X        X            X            X           X          X
```

穷尽搜索 `purchase` / `Supplier` / `vendor` / `采购` / `供应商` / `到货` / `收货` / `PO` 后确认：无模型、无路由、无模板、无迁移、无导航。代码中的 `po` 变量指的是 `ProductionOrder`，与采购无关。

**当前实际做法**：跳过采购，直接手工做原材料入库，供应商名称作为入库表单里的一个文本框填写。

这意味着：原材料从哪来、花了多少钱、什么时候到、谁供的货，系统里没有可追溯的单据。

---

### 阶段 3：物料入库【完整】

```
原材料入库 RawMaterial【完整】   POST /inventory/raw-material/inbound
易耗品入库 Consumable【完整】     POST /consumables/inbound
成品入库   FinishedProduct【完整】 POST /inventory/finished-product/inbound
```

- 原材料按品类 `RawMaterialCategory` 组织，品名通过关联品类取得（`material_name` 是 property，不是列）
- 支持 Excel 导入导出、自动存档

已知缺陷：

- `raw_material_inbound` 中缺品类时走到 `errors.append`，但该变量未定义（应为 `error_messages`），会抛 `NameError`
- 遗留路由 `/inventory/inbound` 仍使用已删除的 `material_name=` 构造参数，属过时代码

---

### 阶段 4：生产计划【部分】

```
销售订单详情 → 创建生产订单
  POST /sales_order/<order_id>/create_production_order
  → 继承销售订单规格，销售订单状态 confirmed → in_production
  → 自动调用 allocate_materials() 按 BOM 展开物料需求
```

**断点：物料分配是空账。** `ProductionOrder.allocate_materials()` 只写入 `required_quantity`（需求量），全仓库**没有任何代码写过 `allocated_quantity` 或 `consumed_quantity`**。所以这张表只是一份 BOM 需求快照，既不预留库存，也不记录实际消耗。

配套的 `check_and_handle_material_shortage()` 检测到短缺后函数体是 `pass`，但返回消息里提到会创建子生产订单，**提示与实际行为不符**，容易误导使用者。

---

### 阶段 5：批次拆分与自动派工【部分】

```
生产订单 → 添加生产批次 ProductionBatch
  POST /production_orders/<order_id>/batches/add
  → generate_product_codes() 生成 ProductionBatchItem 及产品编码
  → create_tasks_for_production_batch() 自动派工
      按 ProductProcess.sequence 逐工序建 TaskAssignment
      查 ProcessAssignmentRule：
        fixed       → 取 sequence 最小的成员
        weighted    → 按 weight 构造员工池后选取
        round_robin → 按 sequence 轮询
      无规则或无成员 → 兜底：全局在职员工轮询
  → 写 AuditLog
```

这是整条链路上**少数完全接通**的环节，三种派工策略都真实实现了。

遗留问题：

- 派工后**不发通知**。`notify_task_assignment()` 在通知服务里已定义，但从未被调用。
- 任务粒度是**批次级**，不是 BatchItem（单件）级，与生产中心的实例视图粒度不一致。

---

### 阶段 6：生产执行【部分，且存在两套并行流程】

**主流程（员工端）：**

```
员工登录 → /my_tasks → 填报完成数量 + 选择实际用料（支持 QR 扫码）
  → POST /tasks/<id>/update_status
  → 达量后创建 ProductionRecord
  → 遍历用料，直接 RawMaterial.quantity -= qty   ← 实扣库存
  → 若用料不在 BOM 内：前端 SweetAlert 确认 + 写 AuditLog + 发替用通知（不阻断）
  → 若 process.needs_inspection：自动创建 InspectionTask
```

**并行的第二套流程（生产中心）：**

```
/production_center → 创建实例 → execute_operation 写 ProductionRecord
```

这套流程**不派工、不扣库存、不触发质检、不入成品库**，与员工端 `/my_tasks` 完全没有打通。这是一个需要你决策的架构分叉点：两套并行的生产执行入口，行为不一致。

其他缺陷：

- `update_task_status` 给 `task.completed_at` 赋值，但 `TaskAssignment` 模型**没有这个字段**
- 扣料只减 `RawMaterial.quantity`，**不回写 `MaterialAllocation.consumed_quantity`** → 计划与实际两本账，无法对账

---

### 阶段 7：质量检验【部分，fail 分支完全断裂】

```
工序 needs_inspection=True → 任务完成时自动建 InspectionTask
  target_type='production_record'，但 template_id 为空   ← 未绑定模板
  → 检验员 POST /api/quality/tasks/<id>/start-inspection（此时才手动选模板）
  → 填写检验项 → POST /api/quality/records/<id>/submit
  → InspectionRecord.result = pass / fail
```

**断点：`result = fail` 之后什么都不会发生。**

`NonconformityRecord` 模型定义了处置类型 `type`（rework 返工 / scrap 报废 / accept 让步接收）、处理人、处理结果，但：

- `quality.py` 只 import 了模型，**没有任何创建或更新的 API**
- `submit_inspection_record` 不处理 fail 分支
- 前端 `records.html` 期待接口返回 `record.nonconformity.handling_method`，而 `get_inspection_record_detail` **根本不返回这个字段**
- 不回写 `TaskAssignment`、不回写 `ProductionBatchItem.quality_status`、不影响库存

也就是说：**不合格品目前只是一条 result=fail 的记录，不触发返工任务、不报废、不扣减、不阻断后续流程。**

---

### 阶段 8：完工入库【断裂】

```
批次完成 → 批量标记 ProductionBatchItem.status = completed
        → update_production_status_hierarchy() 汇总订单 completed_quantity
        → X  不创建 FinishedProduct
```

**生产完工不会自动生成成品库存。** 从 `ProductionRecord` 或 `ProductionBatchItem` 到 `FinishedProduct` 没有任何自动路径。

目前成品进库存只有两条人工路径：

1. 手工新增生产记录时填写「检验员」字段，会顺带创建 `FinishedProduct`（`routes.py` 中 add_production_record 分支）
2. 走库存模块的成品入库页手工录入

---

### 阶段 9：发货出库【缺失】

```
成品出库 → 关联销售订单 → 更新 FinishedProduct.status = shipped → 回写销售订单 completed
   X            X                        X                              X
```

`FinishedProduct` 模型里有 `shipped` 状态，导入模板说明里也提到了，但**没有任何路由会把状态改成 shipped**。销售订单的 `completed` 状态同样需要人工在编辑页修改。

---

### 阶段 10：计件薪资【部分】

```
工资 = Σ(ProductionRecord.quantity × ProcessPrice.price) × Employee.coefficient
       + 奖励 − 处罚 + 基本工资
```

- 端点：`GET/POST /salary_calculation`（admin / accountant）、`GET /salary/<employee_id>`

**注意**：计件工资只依赖 `ProductionRecord`，**与质检结果完全无关**。质检不合格的产出照样计入工资，且由于不合格品没有处置流程，也没有任何扣减机制。

## 三、三条最关键的断链

按对业务闭环的破坏程度排序。

### 断链 1：采购整段缺失

原材料的来源在系统里是空白的。没有供应商主数据，没有采购单据，没有到货记录，无法回答「这批料是谁供的、什么时候到的、单价多少」。当前用手工入库 + 一个供应商文本框顶替。

### 断链 2：质检不合格无处置

`result=fail` 是一条死记录。不合格品不会触发返工任务、不会报废扣减、不会让步放行，也不会阻止产品流向下一道工序或计入工资。质量管控实际上只做到了「记录」，没有做到「管控」。

### 断链 3：完工不入库、入库不发货

生产完成后成品不进库存，库存里的成品也无法发货出库。生产端和库存端、库存端和销售端都是断开的，销售订单从 `in_production` 到 `completed` 完全靠人工点。

此外还有一条**账目层面的断链**：`MaterialAllocation`（计划）和 `RawMaterial.quantity`（实际）是两本独立的账，前者只有需求量，后者被直接扣减，两者无法对账。

## 四、缺口清单（按优先级）

### P0 — 业务流程走不通

1. 采购模块从 0 搭建：`Supplier` 主数据 + `PurchaseOrder` + 到货收货 + 入库联动
2. 不合格品处置：`NonconformityRecord` 的创建 API + fail 处置状态机（返工 / 报废 / 让步）+ 回写任务与批次
3. 完工入库：末工序完成或批次完成时自动创建 `FinishedProduct`
4. ~~物料领用数据不可信：`material_id` 硬编码为 1、不扣库存、跳过审批直接 completed~~ **已闭合**（选真实库存行、按品类审批、发料扣账）
5. `MaterialAllocation` 与实际扣料统一，消除双轨账

### P1 — 功能半成品

6. 成品发货出库 + 销售订单完成状态自动回写
7. ~~物料归还、库存盘点补全 CRUD（当前是「开发中」弹窗）~~ **已闭合**
8. 质检自动任务绑定 `InspectionTemplate`，免去检验员手动选模板
9. 生产中心与员工端两套流程合并或明确职责边界
10. 通知触发器接线：任务分配、工序变更、库存预警等 helper 均未被调用
11. 销售订单新增行补上 `customer_address_id` 保存

### P2 — 安全、一致性与代码质量

12. 导航与角色错位：`base.html` 中生产、库存、销售、系统管理菜单全部包在 `role in ['admin']` 内，manager / hr / accountant / inspector / sales 后端有权限但无入口；`sales` 角色首页直接被拦截，几乎无法使用
13. `/process_prices` 的 GET 缺 `@login_required`；`/products`、`/production_orders`、`/production_records`、`/inventory` 列表页缺角色校验
14. `raw_material_inbound` 的 `errors` 变量未定义会抛 `NameError`；`/inventory/inbound` 为过时遗留代码
15. `TaskAssignment.completed_at` 字段不存在但被赋值
16. ~~`InventoryCount` 状态枚举在模型、表单、统计三处不一致~~ **已闭合**（统一为 planning/counting/completed/cancelled）
17. `MaterialRequisition`、`MaterialReturn`、`InventoryCount`、`Consumable` 等表缺 Alembic 迁移，新环境部署可能缺表
18. 客户地址 API 路由重复注册两次；孤儿模板 `production_order_materials.html`、`process_assignment.html` 无路由引用
19. 审计回滚用 `globals()[target_model]` 反射，且不处理级联（如回滚生产记录不会恢复被扣的原材料）

## 五、待补齐（请在此处标注实际业务）

下列问题需要结合实际业务场景确认，答案将直接决定后续开发方案。

## 六、本轮修复的业务口径影响（2026-09-18）

本节记录 2026-09-18 这一轮开发**改变了哪些业务口径**。第一节表格是当前状态；第二至第四节是改造前记录，与本节冲突时以本节为准。

### 6.1 发货数量口径（用户拍板）

- **一条成品行不再等于一个发货单位**。发货 N 件时按需**拆分成品行**（原行 `quantity -= N` 留库，另建 `quantity = N` 的新行）；**绑定工件的成品行不可拆，只能整行发**。
- 整单发货（`create_shipment`）与按行发货（`shipment_add_item`）两条路径共用 `mes_service.shipment_register_finished_product`，统一校验「本次发货数量 = `min(订单行剩余待发量, 该成品可用在库件数)`」，且**不得超过订单行剩余待发量**。
- 计数单位是**件数**，不是成品行条数（原实现按行数取限，实测「订单 3 件 → 发货明细 11 件」，且完成判定仍判成功）。
- **完成判定改为逐订单行累计**（该行已发 vs 该行订购），不再用全局求和掩盖单行超发/漏发；出库时**只把明细指向的成品行置 `shipped`**，余量保持 `in_stock`。
- 加固：**非整数件数拒绝**；已存档（`is_archived`）的成品行不可发；草稿单占用量计入，同一成品行不会被两张草稿单重复计入。
- 界面：`shipping/detail.html` 新增可选**整数**数量输入，留空即按上式自动取数。
- **副作用（显示口径，非统计错误）**：拆分后同一批库存会显示成 2 条记录，可能被读成「2 件」。已审计确认全仓**没有把成品行条数当件数用的统计**（无 `FinishedProduct.query.count()` / `func.count(FinishedProduct…)`，唯一行数用法是搜索命中条数）。
  - **已定性为「口径决策，不改代码」（2026-09-18 第 8 批）**：界面文案实际写的是「**条**」，**没有「共 N 件」之类表述**——全局搜索 `app/templates/main/search/global_search.html:282` → `库存管理 ({{ …inventory.total }})`（顶部 `:47` 为「共 N 条结果」）；高级搜索 `app/templates/main/search/advanced_search.html:210` → `找到 {{ results.total }} 条{{ category }}记录`。因此 `len()`（`app/services/search_service.py:221` / `:517` / `:538`，语义即「命中 N 条记录」）**保留不动**；若产品仍要弱化歧义，**只建议改文案**。详见 [交付说明-P0P1.md](交付说明-P0P1.md) §6.2 第 23 项。

### 6.2 物料账口径

- `MaterialAllocation` 仍作**计划层**（`required_quantity`），并新增**实扣回写**：报工扣料与领用发料两条通道都会累加 `consumed_quantity`。
- 定位口径：按 `production_order_id` + `material_type` + `material_id` 精确匹配，取 `order_by(id.asc()).first()`；**定位不到就不臆造分配行**（`required_quantity` 非空，凭空建行等于编造计划），只记 warning 并返回 `None`。
- `allocated_quantity` 由 `allocate_materials()` 预置为需求量，并在实扣回写时对 0/NULL 兜底。
- 报工扣料的归集由任务推导生产订单（`write_task_consumed_allocation` → `resolve_task_production_order_id`）；任务未挂生产批次/批次实例时**不回写**，只记 warning。

### 6.3 完工入库时点与门禁口径

- 入库时点 = **末道工序完成后**，产出入正品库（`stock_kind='fg'`）。
- **本次报工自身创建的质检任务不作为本次入库的门禁依据**——否则 `needs_inspection=True` 的末道报工永远不会入库。入库只依据**入库时刻已存在**的门禁状态。
- 质检未通过的产出**单独入未通过库**，不进正常成品库；质检 pass 才放行。
- 已知残余缺口：**无工件产出入库后被改判为不合格时无法回退到未通过库**（工件路径有 `workpiece_blocked` / `dispose_nonconformity` 兜底）。

### 6.4 不合格品处置口径

- 返工 = **新建一条任务**（不是把原任务退回 `in_progress`）；返工工时是否重复计件读 `quality.rework_counts_piecework`（默认 false）。
- 报废 = 扣减已消耗原材料 + 产生报废成本记录 + 报废品**入报废库台账**。
- 让步接收 = 需审批，审批角色读 `quality.concession_approver_roles`（默认 `["admin","manager"]`）。
- 来料检不合格**复用 `NonconformityRecord`**（`target_type` 区分 `production_record` / `workpiece` / `goods_receipt`），支持退货/让步/报废；`pending_inspection` 状态下的强入库后门已封。

### 6.5 权限显示口径

- 目标不变式：**入口可见 ⟺ 端点有能力**（看到即不会 403）。
- 注意一个容易误读的点：「不合格处置」入口用 `can('quality.view')`，而该能力**包含 inspector**，因此 inspector 仍然可见且点击返回 200。原「inspector 会看到但点进去 403」的描述在本次调整后已不成立——改动的效果是让可见性与能力**严格一致**，而不是缩小可见范围。
- 被拒的 `DELETE`/`PUT`/`PATCH` 由 `302 text/html` 变为 `403 application/json`；匿名请求 401 JSON；GET 侧与有权限调用完全不变。

### 6.6 数据正确性口径

- `current_stock` → 真实列 `quantity`；`FinishedProduct.storage_date`（该模型**根本没有此列**）→ 映射到已有的 `created_at`，**不新增列**。
- 同族一并收口：`inventory_inbound` 成品分支、`RawMaterial(material_name=…)`×2、`serial_number=`×2、`completed_date/cancelled_date`、FinishedProduct 挂 Product 的假属性。
- 这类「把 `@property` 或不存在列当数据库列用」的静默失效错误**共复发 5 次**，现已新增静态闸门 `scripts/check_properties.py`（只读、不连库）长期拦截。

### 6.7 `is_archived` 的 NULL 语义（**部分统一**，盘点快照为有意例外）

口径目标：**NULL = 未存档**（`is_archived` 列可空，历史行为 NULL；`== False` 在 SQL 语义上会**排除** NULL 行）。

| 位置 | 现口径 | 说明 |
| --- | --- | --- |
| 发货候选与登记判断（`shipment_candidate_stock`，`mes_service.py:1140`） | ✅ `or_(is_(False), is_(None))` | 2026-09-18 第 4 批统一 |
| `auto_archive_inventory` 自动归档（`app/main/routes.py`，`def` 在 `:6215`） | ✅ `or_(is_(False), is_(None))` | **2026-09-18 第 8 批新增**，**成品与原材料两处**（谓词现 `:6231` / `:6238`），否则历史 NULL 行永远不被自动归档 |
| 质检成品下拉 `get_finished_products`（`app/main/quality.py`，谓词 `:714`） | ✅ `or_(is_(False), is_(None))` | **2026-09-18 第 8 批新增** |
| 盘点快照 `snapshot_inventory_count`（`mes_service.py:1032` / `:1038` / `:1044`） | ⛔ **刻意保留** `filter_by(is_archived=False)` | 语义是「取在库行做盘点」，不是发货/归档候选——**不要改** |
| 库存列表页 `manage_inventory`（`routes.py:4781` 原材料 / `:4792` 成品） | ⚠️ 仍 `== False` | 受页面「显示已存档」开关 `show_archived` 控制；**第 8 批有意未改** |
| 物料搜索 API `api_search_materials`（`routes.py:12037` / `:12065` / `:12094`） | ⚠️ 仍 `== False` | 原材料 / 易耗品 / 成品三处；**第 8 批有意未改** |

- **可以说的**：**发货候选 + 自动归档 + 质检成品下拉**三处已统一为「NULL = 未存档」（第 4 批 1 处 + 第 8 批 2 处）。

- 改动任何一处前请**逐处确认语义**：`is_archived == False` 与 `is_(False) / is_(None)` 在 SQL 上**结果不同**。
- 细节与闸门实测见 [交付说明-P0P1.md](交付说明-P0P1.md) §6.2 第 15、22 项。

- ✅ **`cleanup_temp_files()` 不是缺陷（2026-09-18 第 7 批结论，已修复原耦合）**：它是 `@bp.before_request` 钩子（`routes.py:2196-2200`），**每个请求**都会删除 `TEMP_FOLDER`（= `uploads/temp`，`app/__init__.py:161-163`）中 mtime 超过 5 分钟的文件——但该目录现在是**纯运行时临时目录**（启动时由 `os.makedirs(..., exist_ok=True)`，`app/__init__.py:158/162` 自动重建，只有导入端点往里写上传文件），因此「每请求清理旧文件」是**预期行为**。此前之所以表现为缺陷，是因为该目录**同时**是 6 个受跟踪 Excel 模板的存放目录（已按上一条清理）。⛔ 原「跑前备份、跑完 `git checkout -- uploads/temp/` 恢复」的规避步骤**已废弃**（现在没有可恢复的对象，该命令会报错）。
