### 数据库迁移：单一 head + 禁止 `flask db migrate`

**当前状态（2026-10-11 复测；原记 2026-09-18）**：（历史）峰值 5 个 head，**现为单一 head `p1nonctarget`（35 个修订）**。

```powershell
# HEADS=['p1nonctarget']  head_count=1  revisions=35   → exit 0
```

**schema 的事实来源不是迁移链，而是 `db.create_all()`**：31 张表由 `create_all()` 建出、**不在迁移历史里**，启动时再由 `app/__init__.py` 的 `_ensure_schema()` / `_ENSURED_COLUMNS` 自愈补表补列。因此：

- **禁止 `flask db migrate`**：它会把 `create_all()` 建出的表全部纳入，生成与线上库冲突的巨大脚本。
- 新增表或列：**手写迁移**（`upgrade()` 内做存在性判断保证幂等）**+ 在 `_ENSURED_COLUMNS` / `_ensure_schema()` 中登记**，让老库启动时自愈。自愈才是本项目实际生效的路径。
- **禁止假定迁移链可重放**：2026-09-18 逐层实测结论是**全链重放不可行**，两类阻塞：
  1. 15 个修订里有无条件 `create_table`（`c02604883c72` 一个就建 23 张表），另有约 205 处 `add_column` / `drop_column` / `create_index` / `create_unique_constraint`；实测首处失败 `table process_assignment_rules already exists`。（订正 2026-10-11：**含 `create_table` 的修订文件 14 个**（`create_table()` 调用共 **54 处**；调用点级守卫口径：**2 处有** `has_table` 文本守卫、**52 处无**）；`c02604883c72` 单文件无条件 **24 处** ⇒ 原文「15 个修订 / 一个就建 23 张表」需按此更新；「无 `has_table` 守卫者 11 个文件」本轮未能按文件级复现，**待复核**）
  2. alembic 批量重建**不接受匿名约束**：`ValueError: Constraint must have a name`（`alembic/operations/batch.py:670`）——`create_all()` 建出的表带内联匿名 UNIQUE。
  只给 `migrations/versions/da_add_process_assignment_tables.py` 补了存在性判断（与 `p0p2messtables` / `eb1234567890` 一致），**这不等**于全链可重放（该文件 docstring 里「使整条迁移链可重放」的说法偏乐观，以本条为准）。
- **老库/新库统一走「启动自愈 + `flask db stamp p1nonctarget`」**，完整命令与警告见 [交付说明-P0P1.md](交付说明-P0P1.md) §6.2 第 9 项。

> **必须先把 `DATABASE_URL` 指向目标库**，否则自愈会写到当前配置的那个库上——本项目已因此误写过一次真实 `app.db`（2026-08-27）。

### C-1 迁移链全链重放

**目标**
任意状态的库（空库 / `db.create_all()` 建出且 `alembic_version` 停在任意旧修订的库 / 中途修订的库）
都能仅靠 `flask db upgrade` 升到单一 head **`p1nonctarget`**，不再依赖「启动自愈 + `stamp`」这条旁路。

**范围（inScope）**
- `migrations/versions/`：把 `create_all()` 建出的 **31 张表**补成**正式、幂等**的迁移（现存冻结快照
  `migrations/versions/p0p2messtables_add_create_all_tables.py` 是「表缺失才建表」的存在性判断版本，需评估是否够用）；
- 把**内联匿名 UNIQUE 约束**改为**具名约束**（模型 `__table_args__` / 迁移内显式 `name=`），使 alembic
  `batch_alter_table` 重建表时不再抛 `ValueError: Constraint must have a name`；
- 给 15 个含**无条件 `create_table`** 的修订补存在性判断；核对约 **205 处** `add_column` / `drop_column` /
  `create_index` / `create_unique_constraint` 的幂等性；
- 迁移链的**自动化验证**（新增脚本或扩展现有 `scripts/check_migration_heads.py`），可在 CI 中复跑。

**范围（outOfScope）**
- 不改 `db.create_all()` + `_ENSURED_COLUMNS` 启动自愈（**它是线上实际生效的路径，不得撤除**）；
- 不跑 `flask db migrate` 自动生成（AGENTS.md 明令禁止）；
- 不改 alembic 第三方源码（见「已知障碍」第 1 条）。

**前置条件**
1. 断开「`flask db *` 会先跑 `create_app()` 自愈」这个耦合，或确保全程 `DATABASE_URL` 指向副本
   （⚠ 本项目已因此**误写过一次真实 `app.db`**，2026-08-27）；
2. 准备三类基线库副本：① 空库；② `create_all()` 建表 + `alembic_version` 停 `f179636cecf0`（当前真实库形态）；
   ③ 停在中途某修订；
3. 一份「31 张表 + 全部列/索引/约束」的 DDL 对拍脚本（t5 曾做过对拍，需重做或重建）；
4. 明确 `migrations/versions/` 现状：**35 个修订、单 head `p1nonctarget`**（`scripts/check_migration_heads.py` 可验）。

**验收标准**
1. 三类基线库副本分别 `flask db upgrade` **全部成功**，最终 `HEADS=['p1nonctarget']`、`head_count=1`、`revisions=35`；
2. `upgrade → downgrade → upgrade` 在副本上可重复执行且结果一致（**至少对新增/改动的修订**）；
3. 升级后 DDL（表/列/索引/约束）与 `create_all()` 建出的库**逐项对拍一致**，无残留匿名约束；
4. `scripts/check_migration_heads.py` 与 `scripts/check_db_bootstrap.py` 均 exit 0；
5. 全流程 `DATABASE_URL` 指向副本，**真实 `app.db` SHA256 保持
   `F5DA2306BC31CBAB098AAD3774016D320A9B9AA3546F93418196AE9900E0F065`**（除非显式把副本外某库指定为目标）。

**已知障碍**
1. **alembic 不接受内联匿名 UNIQUE 约束**：`ValueError: Constraint must have a name`，
   `alembic/operations/batch.py:670`（`add_constraint`）——`create_all()` 建出的表带内联匿名 UNIQUE，
   而 `batch_alter_table` 重建表时要求约束具名。属 alembic 内部行为，**不改 alembic 源码或把约束全部改成具名就无法绕过**。
2. **31 张表不在迁移历史里**：必须先把它们补成正式迁移，否则任何「在旧库上继续 upgrade」都会撞
   `table ... already exists`（实测首处失败 `table process_assignment_rules already exists`）。
3. **15 个修订有无条件 `create_table`**（`c02604883c72` 一个就建 23 张表），加约 205 处列/索引/约束操作，（订正 2026-10-11：**14 个修订文件含 `create_table`**（无条件者 11 个文件的文件级读数**待复核**；`create_table()` 调用共 54 处；`c02604883c72` 单文件无条件 **24 处**））
   逐处加固是**线性增长的工作量**，且每加一处都要重跑全链验证。
4. **已撤回的前车之鉴**：captain 曾在 `migrations/env.py` 加全局存在性守卫，实测能让链条多走过建表与索引两处冲突，
   但**仍无法跑通**；由于它改变整个迁移运行时的语义且未经验证，**已撤回**（`migrations/env.py` 已还原）。
   本立项不得以「改 `env.py` 全局守卫」为交付形态，除非有等价强度的验证。

### C-2 两地 PostgreSQL 主从故障切换演练

**目标**
在 `docker-compose.yml` 的 `db`（主）+ `db-replica`（从）双节点上完成**可复现的故障切换演练**，
产出主从切换标准作业程序与丢失窗口量化结论，确认应用侧改动面。

**范围（inScope）**
- 演练三种场景：**主库重启** / **主库停止（非计划切换）** / **计划内主从角色互换**；
- 记录并量化：切换前后复制延迟、**丢失窗口**（允许写已提交但未同步的行）、应用侧需要改动的配置项；
- 核对应用兼容性：`config.py` 已支持 `DATABASE_URL` / `postgres://` 归一化与 `SQLALCHEMY_DATABASE_URI`；
- 产出：`docs/` 下的演练报告 + 操作手册（步骤、判定阈值、回退步骤）。

**范围（outOfScope）**
- 不引入 Patroni / 云托管自动 failover / keepalived 等组件（可作为后续立项）；
- 不做读写分离（应用侧目前只连**当前逻辑主库**）；
- 不改业务代码的写入路径。

**前置条件**
1. **能跑 Docker 的双节点环境**（本机不具备，是这条章程无法在本机完成的根本原因）；
2. `docker-compose.yml` 的 `db` + `db-replica` 可正常拉起（从库宿主机端口 5433）；
3. 用 `scripts/migrate_sqlite_to_postgres.py --sqlite app.db --postgres postgresql://…` 灌入一份**有代表性**的数据
   （含成品拆分行、流水号、审计日志）；
4. 一份可重复的写入压测脚本（产生跨切换的并发写），并预留 `pg_dump` 备份能力。

**验收标准**
1. 三种场景各自演练至少 1 次，每次给出**写入不丢**的对照结果，以及**丢失窗口的量化值**（行数 / 时间窗口）；
2. 应用侧结论明确：**只需改 `DATABASE_URL`** 或**无需改动**（二选一并给出实测证据）；
3. `pg_dump` 例行备份与恢复在演练中**实际跑通一次**（当前尚未建立）；
4. 演练后应用可正常启动并跑通 `scripts/smoke_test.py` / `scripts/functional_test.py`（在指向新主库的前提下）；
5. 产出可执行的操作手册（含判定阈值与回退步骤），并登记在 `docs/` 内。

**已知障碍**
1. **需要能跑 Docker 的双节点环境**（至少两台主机或一台能承受双节点的容器环境），本机不具备；
2. 自动切换需要 Patroni / 云托管 / keepalived 一类组件，超出当前技术栈，需单独选型与排期；
3. `pg_dump` 例行备份**尚未建立**，是演练的前置补充项；
4. 真实故障（网络分区、磁盘故障）在演练环境无法完全复现，只能覆盖「进程/服务级」切换；
5. 两地 Web 当前都连**当前逻辑主库**，**不是双写 SQLite**——演练不得改变这一架构假设。

### C-3 断网多主（工厂与云端同时写入，恢复后合并）

**目标**
工厂侧与云端侧**同时可写**；断网期间各自独立记账；网络恢复后按事先声明的策略完成**冲突检测与合并**，
并保证全过程可审计、可回滚。

**范围（inScope）**
- 流水号避撞（`SITE_CODE` 前缀已实现于 `SerialNumber.get_next_number()`，全局流水号 16 位）的**验证与加强**；
- 冲突检测与合并策略（按实体定义：库存行 / 生产记录 / 报工 / 任务状态 / 单据状态）；
- 审计与回滚（`AuditLog.can_rollback` / `rollback_type` 现有模式需支持**跨库合并**的场景）；
- 合并工具（离线重放 / 差异比对 / 冲突报表）与操作手册。

**范围（outOfScope）**
- 不做实时同步 / 逻辑复制 / 分布式事务；
- 不改现有单主写入语义（默认仍是单主）。

**前置条件**
1. **产品级决策**：冲突优先级规则必须先拍板（**时间戳优先 / 站点优先 / 人工仲裁**三选一或组合），
   以及「哪些字段可自动合并、哪些必须人工确认」；
2. C-2 的演练环境（双节点）作为试验床；
3. 明确**离线期间允许发生哪些写操作**的清单（不是所有实体都适合离线写）；
4. 现有 `SITE_CODE` 前缀机制的实测覆盖范围确认。

**验收标准**
1. 工厂与云端各自断网写入后，恢复并能合并，**不丢实体**（库存 / 生产记录 / 报工 / 任务状态按清单逐项核对）；
2. 冲突行按**事先声明的策略**合并，且**每条冲突都有审计记录**可追溯到「谁在哪个站点改的、依据什么策略裁决」；
3. 合并结果**可回滚**（给出回滚命令与回滚后的一致性证据）；
4. 全局流水号在合并后**无碰撞**（`SerialNumber` 唯一性实测，含 `SITE_CODE` 前缀跨站点场景）；
5. 产出可执行的**写操作矩阵**：逐实体说明「离线可写 / 离线禁写 / 需人工确认」。

**已知障碍**
1. **冲突优先级属产品级决策，业务方尚未确认**（这是本项无法自行推进的首位原因）；
2. 本机为单机环境，**无法演练两地并发写**（同 C-2）；
3. 当前模型大多没有行版本号 / 更新时间戳，**行级冲突检测需要 schema 补充**（属改动范围，需与「手写迁移 +
   `_ENSURED_COLUMNS` 登记」纪律一起排期）；
4. 合并的幂等性与重复重放保护需要设计（合并本身可能被重跑）；
5. 本期已明确「不做断网多主」（见第五节「明确不做」），本立项应视为**下一期的独立课题**，不并入当前批次。
