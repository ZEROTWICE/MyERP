## 三、批次2 的已确认输入

以下为业务方已拍板的决策，直接按此实现，无需再确认。

### 不合格品处置

- 返工：**新建一条任务**，不是把原任务退回 `in_progress`
- 返工工时是否重复计件：读配置 `quality.rework_counts_piecework`（默认 false）
- 报废：**扣减已消耗的原材料** + 产生**报废成本记录** + 报废品**入报废库台账**（实物也要管）
- 让步接收：需要审批，审批角色读配置 `quality.concession_approver_roles`（默认 `["admin","manager"]`）
- 现状：`NonconformityRecord` 只有 6 个字段，需扩展审批状态、审批人、关联返工任务、报废成本等

### 完工入库

- 质检**不止一次**，部分工序后就会质检；**入库时点在末道工序完成后**
- 质检未通过的产出**单独存入「未通过库」**，不进正常成品库

### 物料账

- `MaterialAllocation` 保留为计划层，**新增实扣回写**（报工扣料与领用发料都会调用 `write_consumed_allocation`）
- 领料审批**按材料区分**：`RawMaterialCategory.requires_approval`（默认 True）、`ConsumableCategory.requires_approval`（默认 False）；成品行一律审批。带内部编号的原材料必须选具体库存行

### 其他已确认

- `/my_tasks`（员工手机端）与 `/production_center`（管理员）**两套都保留**，各自负责不同场景
- 发货支持整单发与按订单行分批发，两者都要；需要出库单据和签收回执
- 采购只需「供应商主数据 + 简化采购单」，但完整的请购→审批→采购单→到货→入库流程要一并做好，用配置开关控制不启用

### 数据库迁移：单一 head + 禁止 `flask db migrate`

**当前状态（2026-09-18 实测）**：5 个 head 已收敛为**单一 head `p1nonctarget`（35 个修订）**。

```powershell
& 'F:\Miniconda\envs\wage\python.exe' -B scripts/check_migration_heads.py
# HEADS=['p1nonctarget']  head_count=1  revisions=35   → exit 0
```

**schema 的事实来源不是迁移链，而是 `db.create_all()`**：31 张表由 `create_all()` 建出、**不在迁移历史里**，启动时再由 `app/__init__.py` 的 `_ensure_schema()` / `_ENSURED_COLUMNS` 自愈补表补列。因此：

- **禁止 `flask db migrate`**：它会把 `create_all()` 建出的表全部纳入，生成与线上库冲突的巨大脚本。
- 新增表或列：**手写迁移**（`upgrade()` 内做存在性判断保证幂等）**+ 在 `_ENSURED_COLUMNS` / `_ensure_schema()` 中登记**，让老库启动时自愈。自愈才是本项目实际生效的路径。
- **禁止假定迁移链可重放**：2026-09-18 逐层实测结论是**全链重放不可行**，两类阻塞：
  1. 15 个修订里有无条件 `create_table`（`c02604883c72` 一个就建 23 张表），另有约 205 处 `add_column` / `drop_column` / `create_index` / `create_unique_constraint`；实测首处失败 `table process_assignment_rules already exists`。
  2. alembic 批量重建**不接受匿名约束**：`ValueError: Constraint must have a name`（`alembic/operations/batch.py:670`）——`create_all()` 建出的表带内联匿名 UNIQUE。
  只给 `migrations/versions/da_add_process_assignment_tables.py` 补了存在性判断（与 `p0p2messtables` / `eb1234567890` 一致），**这不等**于全链可重放（该文件 docstring 里「使整条迁移链可重放」的说法偏乐观，以本条为准）。
- **老库/新库统一走「启动自愈 + `flask db stamp p1nonctarget`」**，完整命令与警告见 [交付说明-P0P1.md](交付说明-P0P1.md) §6.2 第 9 项。

> ⚠ **必留的坑**：`flask db *` 会先执行 `create_app()`，而它会跑启动自愈（`create_all` + `_ENSURED_COLUMNS`）。
> **必须先把 `DATABASE_URL` 指向目标库**，否则自愈会写到当前配置的那个库上——本项目已因此误写过一次真实 `app.db`（2026-08-27）。
> 真实 `app.db` 当前 `alembic_version` 仍是 `f179636cecf0`（未 stamp 到 `p1nonctarget`），这是**预期状态**，靠启动自愈保证 schema 齐备。

### 出口网络

- `github.com:443`（HTTPS）**本机常被阻断**；remote 仍是 HTTPS，所以 `git push` 可能直接失败。
- `github.com:22`（SSH）**可用且密钥已登记**。推不上时改用：

```powershell
git push git@github.com:ZEROTWICE/MyERP.git main
```

- ⚠ **remote 名字是 `github`，不是 `origin`**：`git remote -v` 只有 `github https://github.com/ZEROTWICE/MyERP.git`，远端跟踪分支是 **`github/main`**（`git rev-parse origin/main` 会报 unknown revision，不要据此判断「没推送」）。核对远端是否跟上：

```powershell
git rev-list --left-right --count github/main...HEAD   # 输出 "0	0" 即为远端==本地
```
