## 二、批次1 交付内容

### 新增文件

- `app/permissions.py` — 权限能力映射，37 个 capability，导航与路由校验的唯一事实来源
- `app/templates/main/system_configs.html` — 系统配置管理页
- `app/templates/main/welcome.html` — 通用落地页，作为重定向链终点，**不得在此页加任何权限判断或跳转**
- `scripts/check_templates.py` — 模板与权限一致性静态检查
- `migrations/versions/b1a01_add_system_config_and_task_completed_at.py` — 手写迁移

### 关键改动

- `app/models.py`：新增 `SystemConfig`（key-value + value_type，读取带缓存，写入记审计日志且不自动提交）；`TaskAssignment` 补 `completed_at` 字段
- `app/__init__.py`：新增 `_ensure_schema()` 与 `_seed_system_configs()`；原有 SQLite 兼容代码用的 `engine.execute()` 是 SQLAlchemy 1.x API（2.0 已移除），已改为 `with engine.begin()`
- `app/templates/base.html`：整块 `role in ['admin']` 拆为逐项 `can()` 判断
- `app/main/routes.py`：`index()` 按角色分流；15 个列表路由补 `@require_capability`
- `app/main/production_center.py`：`_require_roles` 改为走统一权限表

### 修复的缺陷

1. **重定向死循环**（最严重）：`hr`/`accountant`/`sales` 三个角色此前完全无法登录，`index()` 与 `user_dashboard()` 互相踢皮球。另有一条同类问题：`user` 角色若未关联员工记录同样死循环。现已通过 `welcome.html` 作为终点解决
2. `/process_prices` 缺 `@login_required`，此前匿名可访问
3. `raw_material_inbound` 中两处 `errors` 应为 `error_messages`（同函数内其余五处正确），会让品类校验提示变成含糊的「处理失败」
4. 客户地址 API 同一 URL 重复注册两次，已删除先注册的旧实现，保留支持 `only_active` 的版本
5. 销售订单新增行未保存 `customer_address_id`（编辑路径有），已补

### 验证结论

在 `app.db` 副本上实际启动应用验证，全部通过：表与列自动补齐、5 个配置项落库、bool/json 解析与缓存失效正确、审计日志写入正常、路由注册无重复；八个角色（含一个不存在的角色）访问 `/` 均返回 200 且零重定向循环。

## 三、批次2 的已确认输入

以下为业务方已拍板的决策，直接按此实现，无需再确认。

### 不合格品处置

- 返工：**新建一条任务**，不是把原任务退回 `in_progress`
- 返工工时是否重复计件：读配置 `quality.rework_counts_piecework`（默认 false）
- 报废：**扣减已消耗的原材料** + 产生**报废成本记录** + 报废品**入报废库台账**（实物也要管）
- 让步接收：需要审批，审批角色读配置 `quality.concession_approver_roles`（默认 `["admin","manager"]`）
- 现状：`NonconformityRecord` 只有 6 个字段，需扩展审批状态、审批人、关联返工任务、报废成本等

### 完工入库

- 质检**不止一次**，部分工序后就会质检；**入库时点在末道工序完成后**
- 质检未通过的产出**单独存入「未通过库」**，不进正常成品库

### 物料账

- `MaterialAllocation` 保留为计划层，**新增实扣回写**（报工扣料与领用发料都会调用 `write_consumed_allocation`）
- 领料审批**按材料区分**：`RawMaterialCategory.requires_approval`（默认 True）、`ConsumableCategory.requires_approval`（默认 False）；成品行一律审批。带内部编号的原材料必须选具体库存行

### 其他已确认

- `/my_tasks`（员工手机端）与 `/production_center`（管理员）**两套都保留**，各自负责不同场景
- 发货支持整单发与按订单行分批发，两者都要；需要出库单据和签收回执
- 采购只需「供应商主数据 + 简化采购单」，但完整的请购→审批→采购单→到货→入库流程要一并做好，用配置开关控制不启用
- 到货需要来料检验（`InspectionTask.target_type` 已支持 `'material'`，有现成基础）

## 四、环境与操作要点

这些是排查过才知道的信息，改动数据库或验证时务必先看。

### Python 环境

项目运行环境在 `F:\Miniconda\envs\wage`（Python 3.9.21），依赖完整。系统 PATH 上没有 python。

```powershell
& 'F:\Miniconda\envs\wage\python.exe' -B scripts/check_templates.py
```

### 数据库迁移链已分叉

`migrations/versions` 存在 **5 个 head**，`flask db upgrade` 直接跑会因多 head 失败。数据库实际停在 `0e97d0ec34b4`。

更关键的是：`material_requisitions`、`inventory_counts`、`consumables`、`material_returns` 等表由 `db.create_all()` 建出，**不在迁移历史里**。因此：

- **不要用 `flask db migrate` 自动生成迁移**，会把这些表全部纳入，产生与线上库冲突的巨大脚本
- 新增表或列请手写迁移，并在 `upgrade()` 内做存在性判断保证幂等
- 同时在 `app/__init__.py` 的 `_ENSURED_COLUMNS` / `_ensure_schema()` 中登记，让老库启动时自愈（这是本项目实际生效的路径）

### 验证方式

不要直接拿真实 `app.db` 做验证。通过环境变量指向副本：

```python
os.environ['DATABASE_URL'] = 'sqlite:///' + copy_path.replace('\\', '/')
```

`config.py` 会优先读取 `DATABASE_URL`。

### 权限改动纪律

新增受限功能时，在 `app/permissions.py` 的 `CAPABILITIES` 登记一次即可，模板用 `can()`、路由用 `@require_capability`。改完跑一次 `scripts/check_templates.py`，它会校验模板语法、capability 是否登记、落地页端点是否存在，防止导航与路由再次错位。

### 仓库杂项

- 仓库中提交了 49 个 `.pyc`（Python 3.9 编译产物），清理 `__pycache__` 前务必确认，否则会误删已跟踪文件
- `.gitignore` 目前只有一行规则，未排除 `__pycache__`
- 本地目录名与 GitHub 仓库名不同：目录为 `wage_management_system - bak`，仓库为 `ZEROTWICE/MyERP`，DeepWiki 查询用后者

## 五、产销一体（2026-08-26）

### 数据面

- `DATABASE_URL` 支持 `postgresql://`（`postgres://` 会规范化）；未设置时仍用本地 SQLite。
- `SITE_CODE`（最多 2 位大写）写入 `SerialNumber.get_next_number()`，全局流水号扩到 16 位。
- `docker-compose.yml`：`db`（主）+ `db-replica`（从，宿主机 5433）+ `web`。两地应用连**当前主库**，不是 SQLite 双文件对拷。
- 一次性迁移：`scripts/migrate_sqlite_to_postgres.py --sqlite app.db --postgres postgresql://myerp:myerp@127.0.0.1:5432/myerp`
- 手写迁移 `migrations/versions/c2mespg001_add_mes_columns.py` 只补旧表列；新表仍靠 `db.create_all()`。

### 新模块（路由均在 `app/main/`，权限已登记）

| 能力 | 入口 |
| --- | --- |
| `equipment.manage` | 设备台账、工作中心、装炉图、炉次、工件溯源 |
| `purchase.manage` | 供应商、请购、采购单、到货入库、对账 |

### 业务规则（已实现）

- 炉次禁止无坐标入炉；出炉生成煅烧质检。
- 报工可绑机台与工件编码；`needs_inspection` 时按工件建质检任务，未 pass/未让步不得进入下一工作中心。
- 返工=新建任务；报废入报废库并扣原料；让步读 `quality.concession_approver_roles`。
- 产品 `sellable_as_part`；组装扫自制件 + 按 BOM 扣标准件。
- 采购完整流程由 `purchase.full_workflow_enabled` 控制；来料检 `purchase.incoming_inspection_required`；对账 `purchase.settlement_enabled`。

### 明确不做

- 不删 `/production_center`；不把未通过/报废合成一张正品库存表；不做断网多主冲突合并。

## 六、仓库操作闭合（2026-08-26）

领用/归还/盘点从「开发中」弹窗收口为可记账单据；无工艺路线禁止下生产订单。报工 `/tasks/<id>/update_status` 仍可直接扣料，领用单是另一条仓库通道。本期不强制 BOM。

| 能力 | 行为 |
| --- | --- |
| 领用 | 必须选真实库存行（`material_id`）；`RawMaterialCategory.requires_approval` 默认要审，易耗品默认免审，成品一律要审；发料时扣 `quantity` 并回写 `MaterialAllocation.consumed_quantity` |
| 归还 | `GET/POST /material_returns/add` 关联已完成领用；确认时完好回库，损坏/过期不入正品库 |
| 盘点 | 状态统一 `planning / counting / completed / cancelled`；创建快照 → 录入实盘 → 完成调账 |
| 下生产单 | `add_production_order` / `create_production_order_from_sales` / `create_production_order_from_item` 在 `product.process_items` 为空时拒绝 |

手写列：`raw_material_categories.requires_approval`、`consumable_categories.requires_approval`（`_ENSURED_COLUMNS` + `c2mespg001`）。扣账细节在 `app/services/mes_service.py`。
