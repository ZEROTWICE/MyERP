### P0 — 页面直接 500

**1. `/production_center` 数据超过一页即 500**

`app/templates/main/production_center.html:58` 引用了不存在的模板：

```
{% if pagination and pagination.pages > 1 %}
  {% include 'main/search/pagination.html' %}
```

`app/templates/main/search/` 下只有 `advanced_search.html` 和 `global_search.html`。
实测：当前库 23 条 `ProductionBatchItem`，默认每页 20 → `pages=2` → `TemplateNotFound`；
加 `?per_page=100` 变成一页则返回 200。生产数据必然超过一页，等于该页面不可用。
影响角色：admin、manager。

**2. `/add_production_record` 必然 500**

`app/main/routes.py:4202` 渲染 `main/production_record_form.html`，该模板全仓库不存在
（只在 `routes_full.py` 等备份文件里被引用过）。没有任何模板链接到这个端点，
只能手输 URL 触发，但路由本身是坏的。影响角色：admin、hr。

**3. `/consumables/<id>` 抛 NameError**

`app/main/routes.py:10744` 用了 `Consumable`，但 `routes.py:6` 的顶部 import 清单里没有它
（同文件其他易耗品路由都是函数内 `from app.models import ...` 局部导入，这个漏了）。
所有角色访问都 `NameError: name 'Consumable' is not defined`。

**4. `/material_requisitions` 与 `/material_requisitions/<id>` 抛 TypeError**

`MaterialRequisition.items` 是 `lazy='dynamic'` 关系，返回 `AppenderQuery`，
模板里却用 `|length`：

- `app/templates/main/material_requisitions.html:144`
- `app/templates/main/material_requisition_detail.html:81`、`:133`

改成 `.count()` 即可。领料单模块整个不可用。

**5. `/api/quality/records/<id>/print` 500**

`app/main/quality.py:1331` 传的是自己拼的扁平 dict（`record_code`/`type`/`items`/`base_items`），
`app/templates/main/quality/print_record.html` 期望的是 ORM 对象
（`record.global_sn`/`record.task`/`record.inspector.name`/`record.item_records`/
`record.nonconformity_records`）。两边契约完全对不上，路由和模板像是各改各的。

同一函数里还有三处字段名错误，即使换成 ORM 对象也会继续报错：
`InspectionItem` 没有 `item_name`（是 `name`）、没有 `tolerance`（是 `upper_deviation_value` 等），
`InspectionBaseItem` 同样没有 `item_name`。另外模板第 74 行调用的
`get_inspection_target_name` 只是 `quality.py:954` 的普通函数，从未注册为 Jinja 全局。

### P1 — 功能静默失效（用户点了按钮就失败）

以下四个导出全部是列表页上的 `<a href>` 直连，点击即触发 GET。

**6. `/employees/export`、`/process_prices/export` — 缩进错位导致 GET 恒失败**

```
flash: 导出失败：local variable 'wb' referenced before assignment
```

`app/main/routes.py:2148-2191`（工序价格在 2560 附近同构）：`try:` 块写在了
`if form.validate_on_submit():` 外层，GET 请求走不进 if，`wb` 未赋值就进了 try。
后果有三个：GET 必失败；末尾 `return render_template('main/export_form.html', ...)` 成了永远到不了的死代码；
`finally` 在 `send_file` 之前就删临时文件（Windows 上因文件被占用删除失败并被 `except: pass` 吞掉，临时文件持续堆积）。

**7. `/export_tasks` — 方法名不存在**

```
ERROR in routes: 导出任务数据失败(GET): 'ExcelGenerator' object has no attribute 'generate_tasks_excel'
```

`routes.py:3903`（GET 分支）和 `:3956`（POST 分支）都调 `generate_tasks_excel`，
`app/utils/excel_generator.py:549` 实际叫 `export_tasks`。GET 和 POST 两条路径同时坏，
`AGENTS.md` 里明确要求保留的双支持导出实际一条都不通。

**8. `/inventory/export` — 按实例 API 写的，但那是静态方法**

```
flash: 导出失败：add_headers() missing 1 required positional argument: 'headers'
```

`routes.py:4973` 起连续三处调用签名都不对：`add_headers(wb, headers)` 被当成
`add_headers(headers)`，`add_row(ws, row_data)` 被当成 `add_row(row)`，
`generate_response(wb, filename)` 被当成 `generate_response(filename)`。
这个端点没有任何 UI 引用，是条死路由，但仍对外暴露。

**9. `Employee.status` 是 property，不是列 —— 两处过滤静默返回空**

`app/models.py:146` 的 `status` 是 `@property`（返回 '在职'/'离职'）。
`property == 'active'` 在 Python 里求值为 `False`，SQLAlchemy 把它当恒假条件，
不报错、直接返回空集：

- `routes.py:10490` `api_chart_data_department` → 库里 62 名在职员工，部门图表恒为空
- `routes.py:2155` `export_employees` 按状态筛选 → 一旦选了状态，导出结果恒为 0 条

**10. `/api/chart-data/production` 与 `/api/chart-data/task` 恒报错**

两者都返回 HTTP 200 但 `success: false`：

```
获取生产统计数据失败: type object 'ProductionRecord' has no attribute 'production_date'
获取任务统计数据失败: name 'Task' is not defined
```

`ProductionRecord` 的日期列叫 `date`；`Task` 这个模型压根不存在（任务模型是 `TaskAssignment`）。
`/api/chart-data/salary` 则是写死的示例数组（`8500…9600`，源码里有 `# 暂时返回示例数据` 注释）。
四个仪表盘图表接口只有部门那个"活着"，还因为第 9 条恒为空。

**11. `/audit_logs/rollback/<id>` 回滚删除操作时 500**

实测回滚 `log_id=1`（`rollback_type=add`，`target_model=ProcessPrice`）：

```
HTTP 500 回滚失败：(sqlite3.IntegrityError) NOT NULL constraint failed: process_price_group.process_id
[SQL: UPDATE process_price_group SET process_id=? WHERE process_price_group.id = ?]
```

反射式回滚（`globals()[target_model]`）删除父记录时，SQLAlchemy 默认把子表外键置 NULL，
但 `process_price_group.process_id` 是 NOT NULL。这就是交接文档 P2 清单里
「审计回滚不处理级联」的具体表现，现在有了复现证据。权限本身是好的（user 请求返回 403）。

### P2 — 权限与契约

**12. 三个涉及薪酬的端点没有任何角色校验**

实测 7 个角色（含 `user`、`inspector`、`sales`）全部返回 200：

| 端点 | 泄露内容 | 对应能力表 |
| --- | --- | --- |
| `/salary/<employee_id>` | 任意员工的生产记录、奖惩明细、工资总额 | `salary.view` = admin/accountant |

批次1 收紧的是列表页，这三个是详情/导出端点，没被覆盖到。

**13. 约 30 个 `/api/...` 只读端点无角色校验**

登录即可访问，包括客户搜索、物料搜索、产品搜索、销售订单搜索、
质检任务/模板/记录列表、检验员名单、通知等。数据敏感度低于第 12 条，
但与能力表（如 `customer.manage` 限 admin/manager/sales）不一致。
完整矩阵可用 `permission_matrix.py` 重新生成。

> 修复时复核发现本条严重低估：只统计了 `/api/` 前缀的 GET 端点。
> 全量清点（含 POST/PUT/DELETE、非 `/api/` 前缀）为 **75 条**无任何角色校验，（订正 2026-10-11 口径并列，不得互替：① AST「仅登录、未登记能力」= **8** 条（`app/main` 267 条 `@bp.route` 中的 8 条）；② 运行时「匿名可访问」= **0**；③ 运行时「无校验视图」= **5**（2026-10-08 读数，本轮未复测）；④ 历史基线 = **75 条**（2026-08-11 全量清点，即本处读数）；⑤ 内联 role 白名单 = **16** 条（Python 15 + 模板 1））
> 其中包含 `DELETE /products/<id>`、`POST /products/add`、`PUT /consumables/<id>`、
> `PUT /production_batches/<id>/status` 等破坏性写操作，普通员工均可直接调用。
> 详见第六节修复记录。

**14. JSON API 未登录时返回 HTML 重定向**

```
GET /api/inventory/raw-materials  →  302  text/html  →  /auth/?next=...
```

只挂 `@login_required` 的 `/api/...` 端点走 Flask-Login 默认重定向，
前端 AJAX 拿到的是登录页 HTML 而非 401 JSON。`app/permissions.py:118` 的
`require_capability` 已经正确区分了这两种形式，但这些端点没用它。
违反 `AGENTS.md` 的「禁止 JSON API 返回 HTML」。

> 修复时发现根因比表述的更广：`require_capability` 的 401 分支**从来没生效过**。
> 全仓库的装饰器顺序都是 `@login_required` 在上、`@require_capability` 在下，
> 前者是外层装饰器先执行，未登录请求在它那里就 302 走了，永远到不了后者。
> 即已挂 `require_capability` 的端点同样返回 HTML。

**15. `/api/products/search` 重复注册**

`routes.py:7966 search_products` 与 `routes.py:10118 api_search_products_for_sales`
绑定同一 URL，Werkzeug 按注册顺序只会命中前者，后者是死代码。
交接文档记录批次1 修掉了客户地址 API 的同类问题，这一处还在。

**16. 系统配置页部分提交会连带重置其他开关**

`routes.py:5383` 遍历 `SystemConfig.query.all()`，bool 型一律按
「表单里没有这个字段 = false」处理。只提交一个字段的 POST 会把
`purchase.incoming_inspection_required` 从 true 静默改成 false。
当前页面一次渲染全部配置项，正常操作不会触发；但一旦将来做分类分页保存，
或有脚本/接口发部分表单，就会静默改配置。建议改成只处理表单里出现过的
`cfg__` 前缀字段，或加隐藏字段声明本次提交的 key 范围。

### 第 14 条的真实根因

不是「这些端点没用 `require_capability`」，而是 `require_capability` 的 401 分支
**从未生效过**。全仓库装饰器顺序都是：

```python
@bp.route(...)
@login_required          # 外层，先执行 → 未登录直接 302
@require_capability(...) # 401 JSON 分支到不了
```

改上百处顺序不现实，改为在 Flask-Login 层一次性拦截：`app/__init__.py` 注册
`@login.unauthorized_handler`，复用 `permissions._wants_json()` 判断，
JSON 请求给 401、页面请求维持原有跳转。一次覆盖全部 34 个 `/api/` 端点，
包括本轮没有逐个改的 `chart-data`、质检打印/导出、生产中心明细。

### 新增能力

`code_rule.manage`（仅 admin），否则 manager 在产品页/库存页选不了编码规则；

## 八、第三轮：配置页与全局搜索（2026-08-11）

### 第 16 条：配置页部分提交

`manage_system_configs` 的 POST 遍历 `SystemConfig.query.all()`，bool 型一律按
「表单里没这个字段 = false」处理，于是只提交一个字段的 POST 会把其余开关全部静默关掉。

改为只处理本次提交涵盖的 key：模板对每个配置项渲染一个
`<input type="hidden" name="cfg_present" value="{{ config.key }}">`，
后端取 `request.form.getlist('cfg_present')`，再并上表单里实际出现的 `cfg__` 字段
（兼容不带该声明的调用方），不在这个集合里的配置项直接跳过。

未勾选的 checkbox 不会出现在表单里，所以必须靠这个显式声明才能区分
「取消勾选」和「本次根本没提交这一项」。`functional_test.py` 两个方向都覆盖：
部分提交不误改其他开关，整页提交仍能正常关闭开关。

### 全局搜索：一个此前误判的越权

第四节曾记「`/search` 全局搜索用 `user` 角色搜员工姓名，不会返回员工数据，无越权」。
**这条结论是错的**，当时应该是搜索词没命中。实测：

| 角色 | 搜索结果页含员工工号 | 建议接口返回员工姓名 | 快速搜索命中工序工价 |
| --- | --- | --- | --- |
| user / inspector / accountant / sales | 是 | 是 | 62 条 |

`SearchService` 的 8 类实体（员工、工序工价、生产记录、产品、库存、客户、
销售订单、生产订单）全都没有任何过滤，任何登录用户都能借搜索拿到完整花名册
（姓名、工号、部门、职位）和全部工序工价。这比原先列的第 13 条更严重。

**修法**：`permissions.py` 新增 `SEARCH_TYPE_CAPABILITIES` 映射与
`allowed_search_types()`，把「能搜哪些实体」变成能力表的一部分：

| 实体类型 | 能力 |
| --- | --- |
| `employees` | `employee.view` |
| `process_prices` | `process.view` |
| `production_records` | `production_record.view` |
| `products` | `product.view` |
| `inventory` | `inventory.view` |
| `customers` | `customer.manage` |
| `sales_orders` | `sales_order.manage` |
| `production_orders` | `production_order.view` |

`SearchService.global_search / advanced_search / get_search_suggestions` 增加
**必填关键字参数** `allowed_types`——设成必填而非带默认值，是为了让将来新增的
调用方无法漏传而静默越权。建议接口同样过滤，否则姓名直接从那里漏出去。

上述能力的角色并集是 admin/hr/manager/sales，故新增 `search.use` 能力，
四个搜索端点加 `@require_capability('search.use')`，`base.html` 的搜索下拉
用 `can('search.use')` 隐藏——accountant/inspector/user 一类实体都搜不到，
留着菜单只会点进去撞 403。

### 全量排查 property-当列用（同类错误已第三次出现）

第 9 条 `Employee.status`、上面的 `RawMaterial.material_name`，同一类错误踩了两次，
