## 3. 本轮发现的工程缺陷（新）

### 3.1 ⭐ 「修复前基线」锚定移动 `git HEAD` ⇒ 提交后失效（**系统性**）

| 实例 | 现象 | 根因 |
| --- | --- | --- |
| `w2w3_uatdiff.py`（t9 的 F-3） | tree-before 基准 `git show HEAD:` 已失效，diff 不可复算 | 修复被提交后 `HEAD` 前移 |
| **`w1_p01_probe.py`**（本轮新发现） | **exit 1**：`FAILED: P-01-r2 (pre-fix tree = git HEAD routes.py): row NOT deleted` | 同上——其 prefix 树取自 `git show HEAD:app/main/routes.py`「修复前逐字节」，而修复**已提交**（`fd51023`） |

**影响**：这类探针的**负向对照**在修复提交后必然失败，造成「假红」。
**不影响**：产品修复本身的有效性（`functional_test` 109/0、`w2w3_probe` PASS 已证）。
**修法**：**「修复前树」必须钉显式提交号**（如 `2c6dbfd` = 修复前最后一个提交），**不得**依赖移动的 `HEAD`。

### 3.2 CSRF 判据被统一错误处理器「顺带打断」（`A-69`）

W4/P-12 的统一 `@app.errorhandler(HTTPException)` 把 `CSRFError` 的 400 文案换成「请求参数有误」⇒ `api_matrix` 的 **24 条判据因文案不匹配而误判 `not_enforced`**。
**拦截仍在**（实测 133/133 被拦）。
**双重教训**：① **凡「用文案匹配做判据」的断言，在统一错误处理器引入后必然失效**；② 顺带**诊断信息退化**——`CSRFError` 与普通参数错误无法从文案区分，对排障不利。

### 3.3 待办条目的前提会过时（`C-06`）

`07` 原文称四模块「**既无权限断言也无可达性命中**」，但 `write_suite`/`uat_chains` **早已命中** equipment/purchase_orders/shipments 的可达性 ⇒ 该前提在第一轮分析时即已过时（很可能只算了 `permission_matrix`）。
**教训**：**待办条目自身也需要「前提复核」**，否则第 2 轮会去打一个不存在的靶子。

### 3.4 核验口径本身会失真（本轮连出三例）

| 编号 | 失效形态 | 后果 |
| --- | --- | --- |
| A-71 | 搜索域**漏项**（漏搜 harness/scripts 内容） | 把「已做」报成「未做」 |
| A-73 | 把**概念提及/边界声明**当实现 | 把「未做」报成「已做」（TL-05） |
| A-74 | **自匹配**（搜索域把自己/核验脚本搜进去） | 把「未做」报成「已做」（C-05/C-08/C-09） |

**对策（已下达为全员纪律 `28-第2轮执行纪律.md`）**：`evidence_kind` 四级分级 + 搜索域声明 + `EXCLUDE_BASENAMES` + 「删掉它什么会变红」。
