## 2. 处置口径：默认路径 = 置 `can_rollback = False`（§7.2 拍板项 5）

- **为什么**：`can_rollback=True` 却 `target_id IS NULL` 是自相矛盾的记录 —— 标记为「不可回滚」才是诚实状态；此行**不删、不改任何历史字段**（`action`/`timestamp`/`details`/`target_model`/`rollback_type`/`old_data`/`new_data` 一律不动），只去掉那个按不动的按钮。
- **不做的事**：**不回填 `target_id`**。回填需要从 `new_data` 反推主键，属于**推断**而非事实；一旦推错，等于伪造可回滚能力（比假按钮更危险）。
- **处置后验收判据**（`81-:171`）：`count(target_id IS NULL AND can_rollback = 1)` 由 **10 → 0**（只能在真实 `app.db` 上判定）。
- 用户若对拍板项 5 另有口径（例如「保留标记、改为界面禁用」），本手册的 §6 执行步骤不变，只需替换 SQL 与断言 —— 但**授权要求同样适用**。

**SQL 全文（脚本常量，逐字）**

```sql
-- 正向（整治）
UPDATE audit_log SET can_rollback = 0
 WHERE id IN (7, 8, 12, 15, 24, 29, 40, 44, 68, 73)
   AND target_id IS NULL AND can_rollback = 1;

-- 逆向（还原）
UPDATE audit_log SET can_rollback = 1
 WHERE id IN (7, 8, 12, 15, 24, 29, 40, 44, 68, 73)
   AND target_id IS NULL AND can_rollback = 0;
```

两条 `WHERE` 都带 `target_id IS NULL AND can_rollback = ?` 自限制：既保证幂等（重复执行命中 0 行），也保证不会误碰 `target_id` 非空的 24 行可回滚记录。**内存库阳性对照实测**（§9）：正向命中 10 行、重复执行命中 0 行、逆向命中 10 行且全表行集与初始逐行相同（byte-exact）、对未整治库跑逆向命中 0 行。
