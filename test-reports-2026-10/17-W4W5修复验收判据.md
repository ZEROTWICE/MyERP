## 1. 判据的通用可判定性约定（7 条，全部适用）

- **U-1 三件套齐备**：每条判据必须给 ① **前置数据**（造什么、初始值/状态）② **操作**（方法 + 路径 + 载荷/头）
  ③ **期望状态码 + 正文语义**。缺任一项 ⇒ **不可判定**，不得计为通过。
- **U-2 同响应三元组**：每条判据的断言必须同时看 **状态码 + `Content-Type` + 正文内容**——
  只看状态码会把「404 的 HTML 错误页」误判为合格；只看正文会漏掉 `code=500`（`04` §5.4/§5.5 的实证）。
- **U-3 正负对照成对**：凡「拒绝/不含」类判据必须配「合法请求仍成功」的**阳性对照**（§8 反向约束）。
- **U-4 载体按语义分档**（`04` §5.5 新增口径）：① 200 + `xlsx`/`octet-stream`/`pdf` ⇒ 二进制下载端点
  **不判违规**；② 200 + `text/html` ⇒ **判违规**（契约不一致）；③ 非 200 + HTML ⇒ 看是否 5xx
  （5xx 归缺陷；**4xx 的 HTML 错误页可接受**）。**禁止**一刀切「`/api/` 下非 JSON 即违规」。
- **U-5 口径唯一且可复算**：判据引用的分母一律带「工具 + 口径 + 值」；**`141` 与 `101` 不得互替**、

  （`AGENTS.md` 的 `check_properties.py` 即为防此）或模板渲染值。

## 2. P-09 —— `get_or_404` / `first_or_404` 的 404 被 `except Exception` 吞成 500

### 2.1 业务含义（为什么这是缺陷，而不是「框架限制」）

客户端**无法区分「资源不存在」与「服务器故障」**：业务上「查一个不存在的模板/任务/记录/实例/BOM 行」
是**合法请求**（用户手滑、并发删除、书签失效都会产生），系统应当回答「**该资源不存在**」（404），
而不是「**我坏了**」（500）。判级 **high**（`04` §6 E-3：JSON API 语义错误）。

**判别依据（证明是可修的选择性缺陷，不是框架限制）**：`GET /api/quality/records/999999999`
（**GET、无副作用、无 body**）也返回 500 ⇒ 排除「载荷/夹具」因素；同时**同库另有 121 条带参端点正确返回 404**
（矩阵 C，`04` §5.3）。

### 2.4 判据（每条可直接写成断言）

**P-09-a（主判据：不存在资源必须 404 —— 逐站点，17 处全覆盖）**

- **前置数据**：`app.db` **副本**；已登录且有对应能力的主体（`admin`/`quality.task.manage` 等，按端点能力取得）；
  对 `R1…R6` 还需造一个**真实存在的 `product_id`**（如 1）以隔离「哪个 id 不存在」这一变量；
  哨兵 id = **999999999**（矩阵 C 同口径）。
- **操作**：对 §2.3 的 **17 处**逐个发请求，**只把路径里的资源 id 换成哨兵**（其余参数/载荷保持合法）：
  - 无 body 谓词（GET/DELETE）：直接请求；
  - 有 body 谓词（PUT/POST）：**带合法 JSON body**（避免与 P-12 的 415 混淆，见 §4 的身份隔离规则）。
- **期望**（每条判据断言**三元组**，U-2）：
  1. `response.status_code == 404`（**不得** 500，也不得 200/400/403）；
  2. `Content-Type` 含 `application/json`（若该端点既有契约是 JSON；`print` 端点见下）；
  3. 正文可解析且**含可读原因**，且**不含** `Traceback` / `sqlite3.` / `[SQL:`（与 §3 的 P-11 判据联动）；
  4. **不得**出现「HTTP 200 + `{"success": true}`」这类把「不存在」伪装成成功的形态。
- **计数断言**：`count(status==404) == 17`；`count(status==500) == 0`。
  **红线**：只要 17 处里有**任意 1 处**仍返回 500 ⇒ 该批次判 `needs_revision`。
- **`print` 端点的双层断言（防混判）**：`GET /api/quality/records/999999999/print` 必须 404；
  **不要**在 P-09 里断言它的 `print` 成功路径是 JSON——那是 §6 P-13 的职责。
  即：**P-09 管「不存在 ⇒ 404」，P-13 管「存在时载体是 HTML」**，两条判据不得互相顶替。

**P-09-b（禁止 5xx 同类复发）**

- **操作**：对 §2.3 的 17 处端点，**换 3 种不存在资源形态**各发一次：
  ① 哨兵大整数 `999999999`；② 负数 id（`-1`，若路由为 `<int:...>` 则可命中）；
  ③ 非法类型段（如 `/api/quality/records/abc`）。
- **期望**：① 返回 **404**；② 若路由匹配则 **404**；③ 因路由不匹配返回 **404**（Flask 默认路由 404）
  —— **三种形态均不得出现 5xx**。
- **反向说明（重要）**：③ 的 404 是**路由层**的 404，**不要求**它走端点内的能力校验，
  因此**不得**因「③ 没走到能力校验」判缺陷（避免把 Flask 默认行为当缺陷）。

**P-09-c（静态清单门禁，可机读、非数字漂移）**

- **前置**：`scripts/check_http_contract.py`（TL-02/G-09 的载体，AST `try`/handler 分析）。
- **期望**：输出中「会吞成 500 的站点」**== 0**（当前 **17**）。
  **断言形式**：解析该脚本的机读输出/退出码 ⇒ **exit 0**；若脚本不存在，则退化为
  「人工逐条复核 §2.3 的 17 行 + 记录复核者」，**并在结论里标注口径为人工复核**（不得冒充门禁）。
- **红线**：只把矩阵 C 的违规数从 15 降到 2 而**静态清单仍为 17** ⇒ **不算修好**
  （存量站点未清，只掩盖了实测可见的一部分）。

## 3. P-11 —— 错误响应泄漏异常类名 / 原始 SQL / 绑定参数

### 3.1 业务含义

错误处理把**底层异常 repr** 直接拼进给客户端的正文（`f'…：{str(e)}'`），泄漏**实现细节**：
数据库厂商与版本、表名/列名、**完整 SQL 语句**、**绑定参数值**、Python 异常类名。
业务后果：① 安全面信息暴露（`04` §6 E-5 定级 **medium**，属「安全面」）；
② 把「**可读原因**」降级为「**机器噪音**」——业务人员看不懂，客服无法转述。

### 3.2 现行实测状态（**修前行为**）

| 项 | 实测值 | 口径/来源 |
| --- | --- | --- |
| 命中行数 | **12** 行（矩阵 D 456 条请求中） | `04` §5.4 / §6 E-5 |

| 典型正文 | `{"success":false,"message":"删除失败：(sqlite3.IntegrityError) NOT NULL constraint failed: inspection_records.task_id\n[SQL: UPDATE inspection_records SET task_id=? WHERE inspection_records.id = ?\n[parameters: (None, 1)]"}` | `04` §5.4 / §6 E-4 |

### 3.3 判据

**P-11-a（四类禁用子串，全量扫描）**

- **前置数据**：`app.db` 副本；一份**能触发错误出口的请求集**（矩阵 D 的 456 条同口径，或至少：
  P-10 的删任务、`PUT /api/quality/templates/<id>` 部分更新、`POST /api/quality/tasks` 缺字段、
  `POST /tasks/add` 空表单体、`/api/process_assignment/<id>` 空表单体）。
- **操作**：对每条请求抓 `response.get_data(as_text=True)`；**忽略大小写**做子串命中。
- **期望（四类，缺一不算通过）**：正文命中数 **全部 == 0**：
  1. **`sqlite3.`**（含 `sqlite3.IntegrityError`、`sqlite3.OperationalError` 等**任意** `sqlite3.` 前缀）；
  2. **`[SQL:`**（SQLAlchemy 的完整语句回显；注意**不得**只看 `[SQL:` 而漏掉 `UPDATE`/`SELECT` 语句块本身——
     判据同时命 **`[parameters:`** 与 **`[SQL:` 后缀两段**）；

     —— 形如 `[parameters: (None, 1)]` 的元组/列表文本（判据：`[parameters:` 命中数 == 0）。
- **补充断言（3 条硬性）**：

  3. 表名/列名（如 `inspection_records.task_id`）**不得**出现在正文（并入 ①/② 的实质要求）。

**P-11-b（阴性用例：注入一个回显 `str(e)` 的路径必须被判失败）**

- **前置数据**：在**副本**中构造一个**注入点**（三选一，`t9` 任选并记录所用形态）：
  ① 临时在副本的某个错误出口把 `message` 改为 `f'…：{str(e)}'`；
  ② 用一条**必然触发数据库异常**的请求（如 P-10 的删有关联记录的任务，在**未修**版本上必触发 NOT NULL）；

- **红线**：若注入后判据**仍报通过** ⇒ **判据本身失效**，该批次 `P-11` 的通过结论**一律作废**
  （沿用 `06` §3.1「判据无效 ⇒ 不是产品缺陷，是判据问题」的处置口径）。

**P-11-c（错误详情必须进日志）**

- **期望**：被移除的详情**必须**出现在 `current_app.logger`（ERROR 级）中——判据用**捕获日志**
  （`caplog` 或日志文件）验证，**不得**用「响应体里有没有」代替。

### 4.2 判据

**P-12-a（媒体类型不受支持 ⇒ 4xx，且不得 5xx）**

- **前置数据**：副本；已登录且有能力的会话；对每个被测端点准备**合法路径 + 合法业务参数**（除媒体类型外一切正确）。
- **操作**：对 §4.1 的 **15 条唯一组合**逐条发请求，`Content-Type: application/x-www-form-urlencoded`，
  body 为空表单；**同一请求不变其他任何因素**。
- **期望**：
  1. `status_code ∈ {400, 415}`（**明确建议 415**，因为语义就是「媒体类型不受支持」；
     若实现统一收敛到 400 也可接受，但**必须带可读原因**）；
  2. **绝不允许 `5xx`**（原红线：`== 0`）；
  3. 正文含可读原因，且**不含** §3.3 的四类泄漏子串；
  4. `Content-Type` 为 JSON（对 JSON 端点），**不得**返回 HTML 错误页（`/api/` 面）；
  5. **库不得被改动**（同一断言：请求前后被涉及表的行数与关键字段值相等）。
- **判据形状**：`count(status in {400,415}) == 15`；`count(status >= 500) == 0`；`count(正文泄漏) == 0`。
- **身份隔离（重要，防两缺陷互相顶替）**：这 15 条里**同时**包含 P-09 站点（如 `/api/quality/tasks/<id>`）
  ⇒ 测 `P-12-a` 时**必须用「存在的资源 id」**（否则 404 与 415 会争抢同一个请求，
  使两条判据都无法独立判定）。矩阵 C（P-09）用**哨兵 id + 合法 JSON body**；
  矩阵 D1（P-12）用**真实 id + 错误媒体类型**——**两者不得混用同一请求取证**。

**P-12-b（字段缺失/类型不对 ⇒ 显式 4xx 或正确的部分更新语义，**不得 500**，**不得静默吞错**）**

- **前置数据**：副本；`PUT /api/quality/templates/<id>`（`id` 为**存在**的模板）、
  `POST /api/quality/tasks`（准备一套**其余字段合法**的载荷）。
- **操作与期望**（**逐组合给出可接受出口的闭集**，`t8` 只能在闭集内选一，且**必须一致**）：

| --- | --- | --- | --- |

| `POST /api/quality/tasks` + `{"type": "x"}`（`type` 值非法） | 500 `'type'` | **400** + 可读原因（值不合法） | 500；或 200 建出一个 `type='x'` 的脏任务 |

- **共同断言**：以上任一组合：`status_code < 500`；`库不变`（除 200 的部分更新语义所允许的最小变更）；

## 5. P-10 —— 删除「已有质检记录」的质检任务

### 5.1 现行实测状态（**修前行为**）

| 项 | 实测值 | 口径/来源 |
| --- | --- | --- |
| HTTP | `DELETE /api/quality/tasks/<id>` ⇒ **500** | `04` §6 E-4 |
| 正文 | `{"message":"删除失败：(sqlite3.IntegrityError) NOT NULL constraint failed: inspection_records.task_id\n[SQL: UPDATE inspection_records SET task_id=? WHERE inspection_records.id = ?\n[parameters: (None, 1)]","success":false}` | `04` §5.4 / §6 E-4 |
| 根因（只读复核） | `quality.py:1024` 直接 `db.session.delete(task)`；`inspection_records.task_id` 是 **`nullable=False` + `unique=True`** 的 FK（`models.py:870`）⇒ SQLAlchemy 试图把 `task_id` 置 NULL ⇒ NOT NULL 违约 | `04` §6 E-4 + 本任务只读复核（§11） |
| **触发条件是正常业务操作** | 本组断言「先 `start-inspection` 生成记录，再删任务」 | `04` §6 E-4（判级依据） |
| **既有规则** | `quality.py:997-998`：`task.status in ['in_progress','completed']` ⇒ **400**「进行中或已完成的任务不能删除」；⇒ **`pending` 状态在业务规则上是允许删除的** | `04` §6 E-4 + 只读复核（§11） |
| 路由与能力 | `DELETE /api/quality/tasks/<int:task_id>`（`quality.py:624-634` 的 `manage_task`，`DELETE` 分派到 `delete_inspection_task`） | 本任务只读复核（§11） |
| 判级 | **high**（P-10），REQ-F-04 域 / AC-21 域 | `06` §3.2 |

### 5.2 ⚠ 业务裁定：**删除「有关联质检记录的任务」的正确业务结果 = 拒绝删除（400 + 可读原因）**

> 本项**必须明确、不得含糊**（任务合同硬要求）。以下为**产品侧裁定**，`t8` 必须按 A 实现；
> B 仅在满足全部前置条件时才被接受，**默认判据按 A 执行**。

**裁定 A（本期唯一实现口径，默认判据）**

**删除「已存在关联 `InspectionRecord` 的质检任务」⇒ 拒绝删除：`400` + 可读原因；任务仍在、记录仍在、库其他字段不变。**

理由（三条）：

1. **质检记录是质量可追溯链条的一环**：`InspectionRecord`（`task_id` **非空且唯一**，`models.py:870`）
   一旦存在，它已承载了「谁、何时、按哪个模板、对哪个产出、判了什么结果」。
   用「删任务」这一个动作**连带抹掉质检结论**，在本项目的质量闭环（`07b` DEC-1 的 `quality_status` 语义、
   `NonconformityRecord.record_id` 外键链）里会造成**结论消失而下游状态仍在**的不一致。
2. **与既有规则同向**：`quality.py:997-998` 已确立「进行中/已完成的任务不能删除」（400）。
   「已有质检记录即已开始或已完成质检」在业务上**等价于**该规则，故拒删是**既有规则的自然延伸**，
   不是新增限制（**不扩大限制面**，见 §8 RC）。
3. **可回滚性与可解释性**：拒删是**无副作用**出口（不删任何行），失败可被业务人员理解并转述
   （「该任务已产生质检记录，不能删除」）；而 500 让业务人员以为系统坏了。

**裁定 B（可选的第二阶段增强，**本期不启用**，仅在显式前置下可接受）**

若实现方主张**级联删除**，必须**同时**满足以下**全部**前置，缺一即按 A 判：

1. **显式第二确认参数**（例如 `?cascade=true` 或 body `{"cascade": true}`）——**禁止**默认级联
   （一个删除按钮不得静默销毁质检结论）；
2. 级联范围**明确且有限**：先删该任务关联的 `InspectionRecord`（及其从属记录），再删任务；
   **不得**波及 `NonconformityRecord`（`record_id` 外键链）——若 NC 存在，**必须拒删**；
3. **审计留痕**：`AuditLog` 记录**删除范围**（任务 + 记录 id 列表），`can_rollback=True`、
   `rollback_type='delete'`，`old_data` 含被删记录的关键字段（不满足 ⇒ 判 A）；
4. **不得**借级联删除绕过 `quality_status` 门禁：删掉 `InspectionRecord` 后，
   若 `ProductionBatchItem.quality_status` 的状态机不变量被破坏（`07b` §1.5 第 5 条），判失败。

### 5.3 判据

**P-10-a（主判据：有关联记录 ⇒ 拒删，400 + 可读原因，零副作用）**

- **前置数据**：副本；一个 `status='pending'` 的 `InspectionTask T`（**按既有规则可删**）；
  **已生成**关联 `InspectionRecord R`（`R.task_id == T.id`，满足 `nullable=False`+`unique=True`）；
  记请求前：`task_exists_before = True`、`record_count_before = 1`、被涉及表的行数快照。
- **操作**：`DELETE /api/quality/tasks/<T.id>`（**不带**任何级联参数）。
- **期望**：
  1. `status_code == 400`（**不得** 500、**不得** 200）；
  2. 正文含**可读原因**，且**明确说明原因**为「**该任务已产生质检记录**」而非泛泛的「删除失败」
     （可读性判据：原因文本必须能让业务人员理解「为什么不能删、该怎么办」）；
  3. 正文**不含** §3.3 的四类泄漏子串（与 P-11 联动）；
  4. **零副作用**：`InspectionTask.query.get(T.id)` **仍存在**；`COUNT(inspection_records WHERE task_id=T.id) == 1`
     且 `R` 的 `global_sn/result/inspection_date` **逐字段不变**；

## 6. P-13 —— 路径/载体契约不一致（`/api/` 前缀下返回 HTML / 二进制）

### 6.1 现行实测状态（**修前行为**）

| 项 | 实测值 | 口径/来源 |
| --- | --- | --- |
| `/api/` 端点 | **47** | `04` §5.5 |
| 可解析 JSON | **34** | 同上 |

### 6.2 判据（**按载体语义分档**，U-4）

**P-13-a（`/api/` 面：200 + `text/html` 命中数不得新增，且违规定位可枚举）**

- **前置数据**：副本；对 `/api/` 面的 **47** 个端点逐个发**合法请求**（存在资源 id + 正确媒体类型）。
- **操作**：抓 `(status_code, Content-Type, body 前若干字节)`。
- **期望（分档，逐档断言）**：
  1. **200 + `text/html`** ⇒ **违规计数**。修后 **≤ 1**（即 `print` 端点**唯一保留项**，
     且在 **P-13-c 的登记册**中显式登记）；**不得新增第 2 处**。
  2. **200 + 二进制**（`xlsx` / `octet-stream` / `pdf` / `vnd.openxmlformats-…sheet`）⇒ **不判违规**，
     计数 **== 3**（三条导出端点），且**不得**因本次修复被改成 JSON（改了也不算更好，会破坏前端下载契约，见 §8 RC-5）。
  3. **非 200 + HTML** ⇒ **4xx 可接受**（HTML 错误页）；**5xx ⇒ 归缺陷**（与 P-09/P-12 联动）。
  4. **405 计数 == 6**（Flask 默认行为，**不得**因修复而改变）。
- **红线**：用「一刀切把 `/api/` 下非 JSON 全改成 JSON」来让违规数归零 ⇒ **判失败**
  （会把 3 条导出端点误改成 JSON，破坏 `04` §5.5 第 190 行明文禁止的误报面）。

**P-13-b（`print` 端点的载体必须被**显式裁定**，且 404 语义已由 P-09 修复）**

- **业务含义**：`print` 端点是「打印页」，返回 HTML **本身是设计意图**；
  不一致的是「它挂在 `/api/` 命名空间下」。
- **可接受出口（闭集，`t8` 选一，且**必须写入载体登记册** `P-13-c`）**：
  - **① 移出 `/api/`**：改到页面命名空间（如 `/quality/records/<id>/print`），
    并保留 **301/302 重定向**或前端链接同步更新（判据：新路径 200 + HTML；旧路径 **不得** 500，
    宜 3xx 或 404 且带可读说明；**前端引用必须同步**——全仓搜索模板/JS 引用数 == 0 处残留）。
  - **② 继续挂在 `/api/`，但登记为「设计即打印页」**：判据 = **在 `P-13-c` 登记册中有该行**，
    且该行含 `路径 / 载体 / 理由 / 登记人 / 日期`；`04` §5.5 与 `08` 的报告口径同步更新。
    **不要求**改代码（本出口的本质是「把分歧显式化」）。
  - **③ 统一成 JSON + 文件链接**：返回 JSON（含下载/打印链接），HTML 由独立页面承载。
- **无论选哪个出口**，以下为硬性断言：
  1. `GET /api/quality/records/<不存在>` 与本端点的 **404 语义**必须由 `P-09-a` 的 `Q8` 覆盖（**先修 404**）；
  2. 存在资源时**载体必须与所登记的出口一致**（选①则为 HTML、选③则为 JSON），断言 3 个字段：
     `status_code`、`Content-Type`、`body` 是否符合该出口的契约；
  3. **不得**出现「同一个路径时而 JSON 时而 HTML」的分叉（断言：同一资源连续两次请求 `Content-Type` 相同）。

**P-13-c（载体登记册：可机读，防「悄悄新增」）**

- **判据**：存在一份**载体登记册**（位置由 `t8` 选定并在结论中给出；建议与 `04` §5.5 同口径的机读清单），
  内容为「`/api/` 面非 JSON 载体」的**穷举清单**，每行含 `path`、`method`、`status`、`content_type`、
  `分类（二进制下载 / 设计即打印页 / 违规）`、`理由`、`登记人`、`日期`。
- **期望**：清单条数 **== 4**（3 条 xlsx 导出观测 + 1 条 `print`），
  且「分类=违规」条数 **== 0**（违规必须被消除为「已登记设计」或「已移出前缀」）。
- **断言形式**：解析该清单 JSON ⇒ `len(rows) == 4` 且 `count(分类=='违规') == 0`；
  并与实测扫描结果**逐行一致**（清单与实际不符 ⇒ 判失败：清单不得成为「护身符」）。

## 7. P-08 —— `/tasks/<id>/edit` 的 `notes` 静默丢弃

### 7.1 现行实测状态（**修前行为**）

| 项 | 实测值 | 口径/来源 |
| --- | --- | --- |
| HTTP | `POST /tasks/<id>/edit`（body 含 `"notes": "NEW_NOTES"`）⇒ **200** `{"success":true}`；`quantity`/`status`/`target_date` **正确落库** | `04` §6 E-2 |
| 库内 | 原始 SQL 直读：`notes='OLD_NOTES'`（**未变**） | `04` §6 E-2（`defect_repro.json.cases.edit_notes.db_notes_after_edit='OLD_NOTES'`） |
| 源码（只读复核） | `routes.py:4502-4506` 只赋值 `target_date`/`employee_id`/`process_id`/`quantity`，**无 `task.notes =`**；而 `:4497`（`old_data`）与 `:4532`（`new_data`）**都把 `task.notes` 当「已更新值」写审计** ⇒ `new_data.notes == old_data.notes == 'OLD_NOTES'` | `04` §6 E-2 + 本任务只读复核（§11） |
| 写断言 | `W-TASK-3` **FAIL**（`write_suite.json`；54/51/3 里的 3 条失败之一） | `06` §2.5 |
| 判级 | **high**（P-08）；REQ 无 / **O 域候选**；`06` §4.1 归 **M-6 静默成功/审计失真** | `06` §3.2 |

**业务后果（两条，第二项常被忽略）**：
1. **任务备注无法编辑**——界面返回「成功」但内容不变，用户会反复尝试或误以为系统坏了（**静默成功**）；
2. **审计回滚元数据失真**——`AuditLog.can_rollback=True`、`rollback_type='edit'`，
   但 `old_data.notes == new_data.notes` ⇒ **回滚会把 notes「回滚到同一个值」**，
   即回滚操作**不能恢复**备注的历史，且审计记录**与事实不符**。

### 7.2 判据

**P-08-a（主判据：声明成功 ⇒ `notes` 必须真的变；**仅 200 不算通过**）**

- **前置数据**：副本；一个真实 `TaskAssignment T`，`T.notes = 'OLD_NOTES'`（非空、可区分），
  `T.quantity/status/target_date` 均有确定初值；已登录且有 `task.manage` 能力。
- **操作**：`POST /tasks/<T.id>/edit`，body 含 `{"notes": "NEW_NOTES", "quantity": <Q2>, "status": <S2>,
  "target_date": "<合法日期>", "employee_id": …, "process_id": …}`（其余字段合法且**与初值不同**）。
- **期望（**四条同时成立**）**：
  1. `status_code == 200` 且正文 `success == true`（保持既有契约）；
  2. **库内 `T.notes == 'NEW_NOTES'`**（用**独立连接/原始 SQL 直读**，**不得**只读 ORM 身份映射内的同一个对象——
     `04` §6 E-2 的判别依据正是「`direct view call` 与原始 SQL 直读」）；
  3. 其余字段按既有语义正确落库（`quantity == Q2`、`status == S2`、`target_date == 合法日期`）——
     **不得**为修 `notes` 而破坏既有字段（§8 RC-2）；
  4. **`notes` 之外零额外变更**（同一请求不得顺手改别的列）。
- **判据形状**：`assert resp.json()['success'] is True and db_notes_after == 'NEW_NOTES'`。

**P-08-b（**任务合同硬要求**：审计 `old != new`）**

- **前置**：同 `P-08-a`。
- **操作**：同 `P-08-a`；随后读**最新一条** `AuditLog`（或 `target_model='TaskAssignment' and target_id==T.id`
  的最新行；按 `timestamp`/`id` 取最新，**避免取到历史行**）。
- **期望（**四条，逐条断言**）**：
  1. `log.old_data['notes'] == 'OLD_NOTES'`（**变更前**的值）；
  2. `log.new_data['notes'] == 'NEW_NOTES'`（**变更后**的值）；
  3. **`log.old_data['notes'] != log.new_data['notes']`**（**核心断言**）；
  4. `log.can_rollback == True`、`log.rollback_type == 'edit'`、`log.target_model == 'TaskAssignment'`、
     `log.target_id == T.id`、`log.action == '修改生产任务'`；
     且**其余字段的 old/new 与库内终值自洽**（如 `old_data['quantity'] != new_data['quantity']` 当 `Q2 ≠ Q1`）。
- **红线（**仅看 200 不算通过**）**：出现以下任一 ⇒ 判 `P-08` **失败**：
  - `old_data['notes'] == new_data['notes']`（**本缺陷的核心形态**）；
  - `old_data` 或 `new_data` 缺 `notes` 键（**审计字段缺失**，比相等更糟：回滚没有依据）；
  - `new_data['notes']` 与库内终值不一致（**审计与事实不符**）。
- **可机读形状**：`assert log.old_data['notes'] != log.new_data['notes'] == db_notes_after == 'NEW_NOTES'`。

**P-08-c（阴性对照：**未提供** `notes` 时不得被清空）**

- **前置**：`T.notes = 'OLD_NOTES'`。
- **操作**：`POST /tasks/<T.id>/edit`，body **不含** `notes` 键（其余字段合法）。
- **期望**：`T.notes` **仍为 `'OLD_NOTES'`**（**不得**被写成 `None`/空串）。
- **依据**：`07` §W5 第 13 行的修复口径 `task.notes = data.get('notes', task.notes)`
  ——「缺省即保持」；若实现写成 `task.notes = data.get('notes')`，会把 `notes` **静默清空**，
  那是**新的静默数据破坏**（`RC-2`）。

**P-08-d（通用判据：G-12「声明成功 ⇒ 字段必须变化」，防同类复发）**

- **判据**：`write_suite` 的通用模板新增一条元判据——**凡响应含 `success: true` 的写端点，
  其「本次请求显式提供的字段」必须在库内**发生变化或**与请求值一致**（且若值未变，
  必须能解释为「幂等写入同值」而非「未写入」）。
- **期望**：`W-TASK-3` **FAIL → PASS**；`write_suite` 三态从 **54/51/3** 变为 **54/54/0**
  （或新模板下总数增加而 `failed == 0`；**口径必须写清**，见 U-5）。
- **依据**：`07` §5 G-12「**声明成功 ⇒ 该字段必须变化**（禁静默成功）… 当前 **1 处失败**（P-08）」。
