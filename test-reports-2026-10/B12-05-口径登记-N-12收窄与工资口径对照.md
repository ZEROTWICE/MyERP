### §B.3 财务口径解释（本件职责）

1. **差异来源**：不是数据量变化，而是**同一 `business_date` 换了取的版本**——修前取该 `process_code` 的**首行**（`first()` 无排序 ⇒ 实际取到最早生效版），修后取**业务日前最新生效版**（`effective_date <= 业务日末尾` 且 `order_by(effective_date.desc()).first()`）。
2. **方向可变、幅度不设限**：本夹具为**上调**（`2.5 → 4.0`，单价 `+60%`）；若某工序的历史价高于最新价，则方向为**下调**。故不能把「工资会变」简化成「会变高」。
3. **工资总额分解**：`工资 = base_salary + 计件 × coefficient + 调整`（`app/models.py:129-158` 的 `Employee` 口径：`base_salary` 默认 0、`coefficient` 默认 1.0）。本夹具 `coefficient=1.0`、`base_salary=0.0`、无功过调整 ⇒ **工资差 = 计件差 = +15.0 元 / 10 件**，即 **+1.5 元/件**。
4. **上线前必须做的一次性历史对账**（`81-:131` 风险① 的要求）：对每个 `process_code`，用**同一 `business_date`** 分别计算修前/修后单价，并统计受影响的生产记录**条数、件数、金额差**。本件只交**单一夹具的可复跑读数口径**（工具 + 口径 + 值），不代替全量对账。
5. **口径限制留档（容差，非本批修复项）**：`pick_process_price` 逐字沿用仓库既有约定 `effective_date <= 业务日 23:59:59.999999 + timedelta(days=1)`。夹具 `_T8S9003`（`effective_date = 业务日 00:00 + 1 天`）**仍被取到**（`id=3490 / unit_price=7.77`，`tolerance_picked_future_version=true`）⇒ `81-:107` 阴性栏「`effective_date > 业务日期` 必须被排除」只在「**业务日 + 1 天之后**」严格成立。若要严格排除未来价，须改该约定（属 `app/**`，不在本件范围）。
6. **顺带留档的真实缺陷（不修，只登记，属 `app/**` out of scope）**：当导入 xlsx 的日期单元格是**文本**（如 `"2026-10-09"`）而非真日期单元格时，`/production_records/import` 的 `db.session.commit()` 抛 `StatementError('(builtins.TypeError) SQLite Date type only accepts Python date objects as input.')`（帧：`app/main/routes.py:2865`），被端点外层 `except` 吞成 HTTP 200 + `{'success': false, 'message': '导入失败，请稍后重试或联系管理员'}`、**0 行入库**（`records_written_for_employee` 未增）。
   ⇒ 口径结论：**导入模板的日期必须是真日期单元格**；文本日期行会整批静默失败。证据：`probe_t8_salary_basis_delta.output.json` 的 `A5_text_date_cell_limitation`（含被吞异常类型/headline/栈帧）。
