# 02 — 测试工具链能力评估与差距矩阵（t6）

> 任务：t6 [tooling] 测试工具链能力评估与差距矩阵（依赖 t1 基线事实清单）
> 范围：`scripts/` 下 5 个静态门禁 + 3 个请求型脚本 + 测试脚手架/兼容层/CI 工具
> 纪律：**全程只读生产代码**。本评估未修改任何生产代码/模板/配置/脚本；新建的证据只有本文件与只读探针 `docs/test-reports/_probe/collect_tooling.py`。
> 真实库隔离证据：`app.db` SHA256 = `F5DA2306BC31CBAB098AAD3774016D320A9B9AA3546F93418196AE9900E0F065`，评估开始与结束两次复核一致（= t1 基线值，未被本轮改动）。

## 0. 结论摘要（TL;DR）

1. **静态门禁层是可信的、真会失败的**：5 个脚本里 4 个（`check_templates` / `check_migration_heads` / `check_properties` / `route_inventory`）本轮**原生**（不加任何垫片）exit 0，且都具备"违规即 exit 1"的真实闸门语义；`check_db_bootstrap` 是唯一需要沙箱垫片才能起跑的门禁，但断言最强（幂等 + 整表无遗漏）。
2. **请求型脚本层不可信，但原因不是断言失败**：`smoke_test` 与 `permission_matrix` 返回 exit 1 的**直接原因都是文件写入 `PermissionError`**（`scripts/smoke_test.py:186`、`scripts/permission_matrix.py:129` 的 `../_*.json`），不是发现了缺陷。`smoke_test` 的断言结果为「0 个 5xx / 0 个异常 / 0 个重定向死循环」，`permission_matrix` 的三段结论全部正常。**当前 CI 若按 exit code 判定，这两条会被误判为失败；若人工忽略 exit code，则它们实际上永远不会失败**——后者更危险（见 §3.4）。
3. **最大单点缺口：写路径与负向路径零覆盖**。271 条路由里 110 条非 GET，`smoke_test` 只打 GET、`functional_test` 只有 11 处 POST，**没有任何脚本对 110 条非 GET 路由做过"越权应 403 / 未登录应 401 / 缺参应 400"的负向断言**。t1 复核出的 5 个 P0 业务缺口（质检 fail 零落地、`quality_status` 反放行、返工计件假开关、返工/报废扣料硬编码、端到端表全空）**全部落在这一层，现有工具链一条都拦不住**。
4. **CI 没有任何测试门禁**：`Jenkinsfile` 的「代码质量检查」只 `py_compile main.py`、`py_compile config.py`（flake8 被注释掉），5 个静态门禁 + 3 个请求脚本**一条都没接**（探针 §D 逐项 False）；`.github/workflows/docker-deploy.yml` 只 build+push 镜像；`scripts/deploy.bat` 零测试步骤。测试全靠人工纪律。
5. **`tests/` 是空壳**：`tests/` 下 0 个 `.py` 文件（只有空目录 `static/js` 与 `__pycache__`），无 `pytest.ini` / `pyproject.toml` / `tox.ini` / `setup.cfg` / `conftest.py`；当前 conda 环境 `wage`（Python 3.9.21）**未安装 pytest**（`No module named pytest`）。不存在 pytest 式测试套件，只有"脚本 + 打印"式测试。
6. **沙箱环境是一个必须先分类的失败源**：`route_inventory` / `check_db_bootstrap` / `functional_test` / `smoke_test` / `permission_matrix` 都通过 `_test_bootstrap.make_app()` 用 `tempfile.mkdtemp()` 建库副本；在本沙箱里 `mkdtemp` 建出的 0o700 目录**禁止写入**（实测：0o700 目录写失败、0o777 目录写成功），因此**必须**经 `scripts/_sandbox_compat.py` 垫片才能跑（t1 报告里"全部 exit 0"与之**不一致**，见 §7 X-1）。**结论：任何"exit code ≠ 0"必须先分类为「代码失败 / 环境失败」，再下结论。**

**一句话给下游**：阶段一可以放心把 5 个静态门禁当"真闸门"，把 3 个请求脚本当"复用探针而非门禁"；阶段二必须新建「负向/写路径/业务规则」三层测试，并且把门禁接进 Jenkinsfile，否则 P0 缺口在第 N 次复现时仍然零拦截。

## 2. 逐工具评估

### 2.1 `check_templates.py` —— 模板语法 + 能力登记闭环

- **实际行为**：Jinja2 `env.parse` 全量模板 + AST 读 `app/permissions.py::CAPABILITIES` + 正则收集模板 `can()/can_any()` 与路由 `@require_capability()` + 校验 `ROLE_LANDING_ENDPOINTS` 指向的视图函数存在。
- **实测输出（原生 exit 0）**：`parsed 87 files` / `44 declared / 40 used in templates / 44 used on routes` / `landing 5` / `RESULT: OK`。
- **能挡住什么**：模板语法错误、模板或路由引用了未登记的 capability（漂移）、落地端点写错函数名。
- **挡不住什么**：
  - 只做**声明存在性**校验，不做**能力↔角色矩阵**校验（"admin 能看到但不该看到"这类错误它看不见）；
  - `40 used / 44 declared` 说明 **4 个 capability 只被声明、无人使用**（僵尸能力），门禁不报——`declared - used` 目前不是闸门指标；
  - 模板里 `can('xxx')` 写错能力名**会被挡**（未知能力报错），但模板里 **`url_for('main.不存在的端点')`**（渲染时才炸的 `BuildError`）**不被挡**，这也是模板层最容易漏的一类；
  - 静态正则收集：模板中动态拼接的能力名（如 `can(cap_var)`）不会进入覆盖统计。
- **可信度**：**高**（纯静态、不依赖数据库、输出可复算）。
- **盲区**：`ROUTE_FILES` 硬编码 7 个模块（探针 §A/§B 证明覆盖了所有"有视图"的模块，含 `equipment.py` / `purchase.py`；`sales_routes.py` 是 1 字节空文件、无视图，漏掉无影响）——**本项当前无实际漏扫**，但新增路由模块时必须同步改这个元组，否则能力闭环会静默失效。

### 2.2 `check_migration_heads.py` —— 迁移链单 head

- **实际行为**：用 alembic `ScriptDirectory` **直接读 `migrations/`**，不 `create_app()`、不碰数据库（脚本 docstring 明确记录了这个设计动机：`flask db heads` 会先 `create_app()` → `_ensure_schema()` → 把新表列写进真实库，本项目 2026-08-27 已被该路径误写一次）。
- **实测输出（原生 exit 0）**：`HEADS=['p1nonctarget']` / `head_count=1  revisions=35`。
- **能挡住什么**：迁移分叉（>1 个 head）、迁移链断裂（0 个 head）。
- **挡不住什么**：**迁移脚本 vs 真实库的实际一致性**。本项目 schema 事实来源是 `db.create_all()` + `_ENSURED_COLUMNS` 启动自愈（31 张表不在迁移历史里），"单 head"与"库结构正确"是两件事——最危险的漂移（模型加了列、`_ENSURED_COLUMNS` 没登记、迁移也没写）在本门禁下完全静默。
- **可信度**：**高**（纯静态、零副作用、最快）。
- **盲区**：不校验 `_ENSURED_COLUMNS` 覆盖度；不校验 `migrations/versions/` 里是否有"写了但不在链上"的孤立修订（`walk_revisions()` 只走链）。

### 2.3 `check_properties.py` —— `@property`/不存在列当列用

- **实际行为**：AST 解析 `app/models.py` 建类信息表（assigned/methods/props/bases），再 AST 遍历 `app/` 下所有 `.py`，对 `类名.属性名` 形式报两类违规：A 类「该类上的 `@property` 被类级访问」，B 类「该类及其项目内基类都没有这个名字」。
- **实测输出（原生 exit 0）**：`已扫描 23 个文件，模型类 74 个` / `RESULT: OK`。
- **能挡住什么**：项目**复发 5 次**的那类静默错误（`Employee.status == 'active'` 恒假过滤、`RawMaterial.material_name.like(...)` 抛 `AttributeError` 被吞、`FinishedProduct.current_stock` 这类根本不存在的列）。
- **挡不住什么（设计边界，docstring 已声明）**：
  - 只认 `类名.属性名` 的**类级**访问，`instance.property` 无法静态判定；
  - 只解析 `app/models.py` 一个文件里的类，**服务层/别的模块里定义的类不在名单**（`app/services/*.py` 里如果有自己的类，其属性名不受检查）；
  - `getattr(model, 'name')` / `f'{model}.{col}'` 这类动态用法绕过检查。
- **可信度**：**高**（纯静态、不导入应用）。**注意**：它只保证"名字存在"，不保证"这个列在库里真的存在"——库列口径要靠 `check_db_bootstrap` / 探针。

### 2.4 `route_inventory.py` —— 路由清单 + 重复注册

- **实际行为**：`make_app()` 后遍历 `app.url_map`，按 `(method, path)` 聚合检测重复注册，并按"GET 无参 / GET 带参 / 非 GET"三分类打印全量清单。
- **实测输出**：原生 exit 1（`mkdtemp` 目录写入 `PermissionError`，§6.1），加垫片后 **exit 0**：`total rules=271` / `duplicate (method,path) registrations=0` / `GET no-arg=104 GET with-arg=56 non-GET=110`。
- **能挡住什么**：端点重复注册（同 method+path 挂两个 endpoint）——这类问题在 Flask 里表现为静默覆盖。
- **挡不住什么**：
  - **没有任何断言**，唯一返回码是 `0`（§3.4 说明：它天然不可能失败，除环境错误外）；
  - 不校验"路由↔模板"闭环（GET 端点无对应模板、模板 `url_for` 指向不存在端点）；
  - 不校验方法集合的合理性（该 POST 的写成 GET、缺 CSRF 豁免声明）。
- **可信度**：**中高**（口径权威，因为它直接读 `url_map`，是"路由总数 271"的**唯一权威来源**；但它需要能 `create_app()`，因此依赖库副本环境）。

### 2.5 `check_db_bootstrap.py` —— 空库自举 / 幂等 / 整表无遗漏

- **实际行为**：把 `app.db` 拷成种子库，在临时空库上 `create_app()` 三次（首次 / 再次 / 无种子），断言：自举后有账号、哈希长度合法（102/162）、二次启动不重复导入、哈希不被改写、无种子库时安全跳过；再绕过自举直接 `copy_sqlite_into()`，断言"一行没拷进去"与"整张表被跳过"都不发生。
- **实测输出（垫片下 exit 0）**：`种子库账号数=64` / `首次 64，再次 64` / `无种子库时 0` / `直接拷贝 6712 行，跳过 0 张表` / `OK`。
- **能挡住什么**：这是**唯一**覆盖"老库升级路径"的门禁——拷贝顺序、列匹配、空库判定、幂等。docstring 记录了它的存在理由（`DATETIME` 列曾因裸 SQL 读成字符串让 24 张业务表全军覆没，而账号数断言照样通过，所以必须单独盯 `skipped`）。
- **挡不住什么 / 需注意**：
  - **它和真实库的行数口径差 1**：这里报 **6712 行**，t1/探针的库内总行数是 **6713 行**。差 1 是 `copy_sqlite_into()` 拷贝时排除了某张表（`alembic_version` 是首选嫌疑），但脚本本身**没有交叉校验源库行数**，所以这个差值不会被任何门禁发现（§7 §8.4 口径差异的成因在此）。
  - 只验证"表没被整张跳过"与"行数>0"，**不逐表比对行数**；部分行级丢失（如若干行因类型问题被跳过）不会被发现。
  - `main()` **没有 `sys.exit(...)`**，成功靠隐式 0、失败靠未捕获异常（`AssertionError`）→ exit 1。结果可用但语义不显式。
  - 沙箱内**必须**加垫片（`mkdtemp`），因此它是"最容易被误判为坏门禁"的一个。

### 2.6 `smoke_test.py` —— 全角色 GET 冒烟

- **实际行为**：8 个 actor（anonymous + 7 角色）对全部可达 GET 路由（带参的用库里真实首个 ID 填充）各发一次请求，记录状态码、重定向链（最多 12 跳，检测死循环）、500 响应体，最后把明细写 `../_smoke_results.json`。
- **实测输出**：`[plan] 可测 GET 路由 148 条，跳过 9 条`；每个 actor 148 条；`[done] anonymous…user` 8 行；异常汇总打印 `无 5xx / 异常 / 重定向死循环`；**exit 1**——原因见下。
- **exit 1 的真因（本轮实测，决定性）**：

  ```
  File "...\scripts\smoke_test.py", line 186, in run
      with open('../_smoke_results.json', 'w', encoding='utf-8') as f:
  PermissionError: [Errno 13] Permission denied: '../_smoke_results.json'
  ```

  即：**断言全通过，写结果文件被沙箱拒绝 → exit 1**。`permission_matrix.py` 是同一形态（`:129`）。→ 对下游的直接含义：**"smoke_test exit 1"不是缺陷信号**，t1 报告里"断言 0 问题但 exit 1"已独立复核确认，本评估给出机制级解释并复现。
- **明细数据的二次解读（本轮用 `_smoke_results.json` 复算）**：admin 的 148 条里 **首跳 200 = 144、302 = 4；终态 200 = 148；0 异常、0 死循环、0 个 302→非 200**。也就是说——**这个"冒烟"对 7 个角色 × 148 条 URL 全绿，一个问题都没报**。全绿的原因见 §4：它只证明"没 500/没异常"，不证明"权限对/数据对"。
- **挡不住什么（缺口清单）**：
  - **只打 GET**：110 条非 GET 路由零覆盖；
  - **不判对错**：只看 5xx/异常/重定向循环，403 该不该 403、200 是不是越权返回，它不管；
  - **参数化不完整**：55 条 GET 带参路由中 46 条可解析、**9 条永远跳过**（`PATH_MODEL` 缺前缀映射）：
    `/api/material_requisitions/<int:id>/issued-items`、`/equipment/<int:id>/layout`、`/heat_lots/<int:id>`、`/inventory_counts/<int:id>`、`/material_returns/<int:id>`、`/purchase_orders/<int:id>`、`/shipments/<int:id>`、`/stock/<kind>`、`/workpieces/<int:id>`。
    **这 9 条恰好集中在 `equipment/purchase/shipping/stock` 四个模块**——而 `permission_matrix` 的守卫扫描又恰好漏掉这四个模块（§2.7），**两处盲区重合**，形成"四模块双层盲区"；
  - 写死 3 条 SKIP（`/auth/logout`、`/auth/register`、`/bootstrap/static/<path:filename>`）无理由记录，无法审计"为什么跳过"；
  - **只跑单请求**：无并发、无事务边界、无幂等复跑（同一 URL 打两次）；
  - CSV/明细不含"该角色应当是什么结果"的期望值 → 结果无法自动判定，只能人工看。
- **可信度**：**中**（覆盖面不错、噪音低，但"全绿"没有信息量，且 exit code 不可用）。

### 2.7 `permission_matrix.py` —— 权限矩阵

- **实际行为**：对每个 GET 路由，用 8 个 actor 抓 `follow_redirects=True` 的结果，按「权限不足文案 / 401 / 403 / 登录页特征」分类成 OK / DENY / LOGIN / HTTPxxx；再打印三段：① 匿名可访问（应为 0）② 所有登录角色都能访问 ③ 源码上完全没有校验的视图；最后写 `../_permission_matrix.json`。
- **实测输出（本轮全文复核）**：
  - ① 匿名可访问 = **0**（`无`）；
  - ② 所有登录角色可访问 = 6 条：`/ [main.index] guards=['inline_role_check']`、`/api/notifications/recent`、`/api/notifications/stats`、`/my_tasks`、`/notifications`、`/user_dashboard`（后 5 条 `guards=['NONE']`）；
  - ③ 源码无校验视图 = 同样 5 个：`api_notification_stats`、`api_recent_notifications`、`manage_notifications`、`my_tasks`、`user_dashboard`；
  - **exit 1**，原因是 `:129` 写 `../_permission_matrix.json` 的 `PermissionError`（与 smoke_test 同形）。
- **可信度分档（本评估的关键判断）**：
  - ①「匿名可访问=0」**可信**（这是实测请求结论，不是推断）——**但只覆盖 GET**：110 条非 GET 路由的匿名访问**完全没测**；
  - ② ③ 两段是**提示而非判定**，且本轮明确显示为**假阳性**：这 5 个视图按 `AGENTS.md`「新增路由默认加 `@require_capability`；确实所有角色都要用的，才只留 `@login_required`」属于**有意为之的登录即用型页面/接口**（我的任务、用户面板、通知列表及其 API）。`functional_test` 已反向验证过其中 `/api/*` 匿名访问返回 401/JSON。→ **这 5 条不应作为缺陷上报**，但脚本把它们和真缺陷混在同一段输出里，容易被下游误读为 P0；
  - `guards` 判定是**正则/AST 混合的启发式**：函数体只看前 25 行、装饰器向上收集时遇到"空行即停"，长函数里的 `current_user.role` 判断会漏检（探针实测：`quality.py` 有 12 个、`routes.py` 有 2 个体现在函数体里的 inline role 判断，与 t1「Python 15 处内联 role」是同一批，但门禁只报告 3 个文件范围内的结果）。
- **结构性问题（比假阳性更重要）**：
  1. **它永不失败**：`run()` 结尾 `return 0`，无论 ①②③ 打印出什么。即便匿名可访问 50 条，exit code 仍是 0。**这是"看起来是门禁、实际是报告"的典型**；把 exit code 接进 CI 只会得到一个恒真的绿灯。
  2. **守卫扫描漏 47 个视图**：`ROUTE_FILES` 只有 3 个模块（`routes.py` / `quality.py` / `production_center.py`），而探针实测 `equipment.py`(15) + `purchase.py`(20) + `shipping.py`(7) + `stock.py`(5) = **47 个视图**的守卫类型完全不在识别范围内（`guards.get(func)` 会返回 `None`/`UNKNOWN`）。
  3. `denied` 判定依赖中文字符串 `'权限不足'` 与登录页特征 `'name="username"'`——文案一改，判定就静默失效。

### 2.9 结果产物与路径依赖（容易被忽略的"可信度杀手"）

- `smoke_test.py:186` 与 `permission_matrix.py:129` 都写 **相对路径 `../_*.json`**：
  - 从仓库根原生执行 → 落到**父目录**（`D:\workspace\_smoke_results.json`，实测该处确有同名文件，33679 / 135512 B）；
  - 经垫片执行（`chdir` 到 `scripts/`）→ 落到**仓库根**（`_permission_matrix.json` 33679 B、`_smoke_results.json` 135512 B，两者都在 `.gitignore` 的 `/_permission_matrix.json`、`/_smoke_results.json` 条目内，`git status` 干净）；
  - **两个位置的文件同时存在**，谁是最新一次运行的结果无法从文件名判断，只能看 mtime。
- 写入**没有 try/except**：写失败 → 异常 → **exit 1**，把"测试通过"污染成"测试失败"。这一条同时是 §2.6/§2.7 exit code 不可信的根因。
- 无 CLI 参数、无 `--json-out`、无固定报告目录，产物不可重定向到 `docs/test-reports/` 下归档。

### 2.10 `functional_test.py` —— 唯一真正"断言式"的请求测试

- **实际行为**：模块级 `PASS/FAIL` 列表 + `check(name, ok, detail)` 自建断言框架，11 个测试函数：系统配置（含缓存失效、审计日志、复选框部分提交）、Excel 模板/导出 GET、导出表单 POST、25 个 JSON API 契约、未登录 JSON 返回形式、5 条不存在资源应 404、全局搜索与角色可见范围、任务写操作（403/400/成功/完成态）、无工艺路线禁止下单、领用发料扣账、盘点调账、启动自愈幂等（子进程内两次 `create_app()`）。
- **实测输出（垫片下 exit 0）**：`结果：109 通过 / 0 失败`。
- **可信度**：**高**（三种脚本里唯一"通过=有意义"的一条；exit code 可信且它**不写仓库根**，与 t1 的 X-12 结论一致）。
- **挡不住什么**：
  - **硬编码清单**：11 个函数里的 URL 是手写枚举（25 条 JSON API、12 条下载、5 条 404），**新增路由不会被自动纳入**；
  - **顺序耦合**：模块级可变状态 + 每个函数对同一份临时库做写操作，`run()` 顺序执行；函数间共享 `app`、依赖前面的副产物（如 `_t_admin` 用户、`_功能测试` 记录）；
  - **无参数化/无 fixture 隔离/无 pytest**：失败时的定位靠打印；
  - **时间相关硬编码**：`target_date='2026-12-31'`、`planned_start_date='2026-09-01'`、`requisition_date='2026-08-26'` 等固定日期，跨时间窗会漂移（季节/日期校验一改就会假失败）；
  - **业务覆盖薄**：质检（`quality.py` 32 个视图）、采购（20）、设备（15）、发货（7）、库存（5）、生产中心（7）**几乎没有功能断言**——t1 复核的 5 个 P0 缺口（报工质检 fail 零落地 / `quality_status` 反放行 / 返工计件假开关 / 返工报废硬编码扣料 / 端到端表空）**一条都不在 109 条断言里**；
  - **无负向矩阵**：只有 3 处 403 断言（`user 新增任务被拒`、`user 改他人任务被拒`、`user 删除任务被拒`）+ 若干 400，覆盖的是 `/tasks/*` 一族，**其余写端点的"越权应拒"零断言**；
  - **导出口径偏弱**：只断言 `Content-Type` 含 `spreadsheet` 与字节数，**从不打开 xlsx 校验内容/表头/行数**（`openpyxl` 已在环境里，成本很低）；
  - **无并发/无事务回滚断言**：t1 指出的"超量提交"漏洞在这里只测了单请求 400/正常路径。

## 5. 环境与可重复性风险

1. **沙箱/受限环境的 `mkdtemp` 陷阱（已复现，机制明确）**
   - 实测：在 `tempfile.gettempdir()`（`…\Temp\dsh-SGEvR5`）下 `os.mkdir(path, 0o700)` → 目录可建但**写入被拒**；`os.mkdir(path, 0o777)` → 写入成功。`tempfile.mkdtemp()` 固定 0o700。
   - 影响面：`route_inventory.py`、`check_db_bootstrap.py`、`functional_test.py`、`smoke_test.py`、`permission_matrix.py`（凡走 `_test_bootstrap.make_app()` / `mkdtemp` 的）。
   - 现状：`scripts/_sandbox_compat.py` 提供了不侵入被测脚本的垫片（只放宽 tempdir mode + 子进程输出通道），**本评估所有请求型/建 app 类结论均在垫片下取得**。
   - 建议（阶段二）：把这一条写入 runbook 的"环境前置条件"一节：**"本沙箱内凡 exit≠0 的脚本，先判定是否为 `PermissionError: mkdtemp` / `../_*.json`，再判定为代码失败"**；或给 `_test_bootstrap` 加 `TMPDIR` 可配置 + 仓库内临时目录回退（**注意：这会改生产无关的脚手架脚本，需在阶段二获批后做**）。

## 6. CI/部署侧评估（工具链的"最后一公里"）

1. **Jenkinsfile（探针 §D 逐项实测）**：
   - `stage('代码质量检查')` 只跑 `python -m py_compile main.py` 与 `python -m py_compile config.py`；flake8 一行被注释；
   - **5 个静态门禁 + 3 个请求脚本 + pytest 全部未接入**（逐项 False）；
   - 该 stage 用 `try/catch` 把异常降级为 `currentBuild.result = 'UNSTABLE'`——**UNSTABLE 在 Jenkins 里是"不失败"**，且下游 stage 不 `error`，所以即便 py_compile 失败也不阻断部署；
   - `stage('数据库迁移')` 用裸 `python -c "...flask_migrate.upgrade..."`：**没有先 `set DATABASE_URL`**，也没有走 `AGENTS.md` 明令的「启动自愈 + `flask db stamp p1nonctarget`」路径。这正是文档里"已因未指向副本而误写真实 `app.db`"的同类形态，属**部署侧高危**（本评估只报告，不改动）；
   - `stage('健康检查')` 只 `curl -f http://localhost:5000/`：`/` 是 `inline_role_check` 的落地页，对匿名/任意角色都能返回 200——**健康检查不具备实质验收力**；
   - 失败分支的回滚只尝试恢复 `app.db`，不回滚代码/模板。
2. **GitHub Actions**：`.github/workflows/docker-deploy.yml` 只做 build + push（无测试、无门禁）。
3. **结论**：当前"门禁"是**人工纪律**，不是自动化闸门。阶段一交付的测试方案若要求"每次变更必跑 X"，必须在 `t7` 的 runbook 里同时给出"接进 Jenkinsfile 的具体 stage 片段与失败语义（`error` 而非 `UNSTABLE`）"，否则方案落地率不可保证。
