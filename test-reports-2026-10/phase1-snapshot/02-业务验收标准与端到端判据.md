## 0. 使用约定（给下游：t5 / t6 / t7 / t8 定稿）

1. **每条 AC 五元组**：`编号 | 业务判据 | 判据载体（表/字段/端点） | 生效状态 | 验证方式`。
   - **判据载体必须落到「可查的表.字段」或「可点的端点」**，不接受「页面看起来对」这类不可判定的写法。
2. **生效状态三档**（决定该 AC 是「回归项」还是「待修项」）：
   - `✅ 已实现` = 当前源码已具备该能力 → 验收 = **回归**（现状通过才算通过）。
   - `⚠ 部分` = 有路径但不完整 → 验收 = **回归 + 明确记录残余**，**不得**因部分通过就整条判通过。
   - `❌ 未实现` = 现状必然不通过 → 验收 = **缺陷回归项**；在批次4/5/6/7 修完前，**该 AC 的期望结果按「应然」写，实测按「实然」记录**（这正是验收要暴露的差异）。
3. **数量单位一律是「件数」**，不是「行数」。判据写法固定为
   `SUM(FinishedProduct.quantity) WHERE stock_kind='fg' AND status='in_stock'`。
   ⚠ 依据：`业务流程现状与缺口.md` §6.1 已拍板「一条成品行 ≠ 一个发货单位」（发货会按需拆分成品行）；
   历史事故「订单 3 件 → 发货明细 11 件」正是在「按行数判」的门禁全绿下发生的。
4. **禁止用 smoke 当验收替代**（规划 D-8）：`smoke_test` 只覆盖「GET 是否 5xx/重定向死循环」，
   数量/金额/状态机必须有独立断言。
5. **凡「文档说已修」不算通过**（规划 D-9）：每条 AC 必须给出可复跑的判据；
   本文件对无法在本机复现的项**显式标注**（不写成已通过）。
6. **三份「不冲突但会误读」的口径**（基线 §8.4 / §8.5，引用时必须带口径）：
   表数 75（含 `alembic_version`）/74（metadata）；行数 6713/6712；能力使用 43（正则）/44（AST）；
   无校验三个量纲 **75（历史）/5（当前视图）/15+2（当前内联 role）不得互替**。

### 4.2 ⚠ 三个必踩的夹具陷阱（本轮实测）

1. **成品库「有 2 行但一件都发不了」**：真实库 `finished_product` 两行为
   `(id=1, FP001, quantity=10, status=in_stock, stock_kind=NULL)` 与 `(id=2, FP002, quantity=5, ...)`。
   `/stock/fg`（`stock.py:20` `filter_by(stock_kind='fg')`）与 `shipment_candidate_stock`
   （`mes_service.py:1150` `stock_kind.in_(SHIPPABLE_STOCK_KINDS)`）**都排除 NULL** →
   **发货链（AC-40…AC-46）必须先用报工/入库动作造出 `stock_kind='fg'` 的行**，否则用例会「取不到候选」而被误读成缺陷。
2. **原料只有 1 行、数量 1.0** → AC-29 系列的 `N ≠ 1` 与「多消耗行指向不同 `raw_material_id`」

3. **`is_archived` 的 NULL 语义**：真实库 `finished_product` / `raw_material` 的 `is_archived` 均为 `0`（**非 NULL**），
   AC-56 的「统一前看不到 / 统一后看得到」**必须显式 `UPDATE ... SET is_archived=NULL`** 造行，
   否则会把「没测到」当「测过了」（规划 §3.2 批次8 验收 2 已点名同一陷阱）。

### 5.3 可照做的手工验收清单（业务语言，非作者执行一次）

1. **角色与入口**：分别用 7 个角色登录 → 看首页是否 200、菜单是否出现自己该有的项 →
   **逐个点击**菜单项，确认「看得到的不 403」（AC-01/02）。
2. **报工质检**：对 `needs_inspection=True` 工序报工 → inspector 提交 `fail` →
   打开 `/quality/nonconformities` **是否新增 1 条、能否看出对应哪张生产记录** →
   再对同一订单报工一次，看 `/stock/fg` 是否**新增 0 件**并给出**能读懂的原因** →
   把该单处置为完成后再报工，看是否**恢复入库**并入库件数正确（AC-13/14/15/12d）。
3. **工资差分**：`rework_counts_piecework=false` 走一条返工，记录 `/salary_calculation` 区间数字 →
   配置改 `true` 重跑**同一场景** → 数字必须**不同**；再跑一条非返工场景 → 两次必须**相同**（AC-25/26/27）。
4. **不合格页可用性**：打开 `/quality/nonconformities` → 类型/状态是否为**中文** →
   对来料检行是否**有到货单入口、无「返工」按钮或给明确说明** →
   点「返工」不选工序/员工提交，是否给**可读提示**（AC-21）。
5. **让步审批不漏单**：无权用户点「让步」→ 审批人用「待审批」筛选**只**看到该行 → 审批后状态正确（AC-22）。
6. **通知到达**：派工一次 → 被派工员工登录看 `/notifications` 有 1 条；
   把某原材料库存降到低于阈值 → 产生预警；**不满足规则的员工无通知**；连续触发两次**只 1 条**（AC-48/49/50）。
7. **仓库单据**：领用 → 发料（看库存与计划账同时变）→ 归还（库存回增）→ 盘点（库存被写成实盘数）（AC-33/34/35）。
8. **发货**：造好 `stock_kind='fg'` 的在库行 → 整单发 + 按行发各一次 →
   核对「**件数**守恒」而不是「行数」→ 出库 → 签收 → 订单 `completed`（AC-40…AC-46）。
9. **迁移后真实库零改动**：三类基线库副本各跑 `upgrade` 两次 → 真实库 SHA256 不变、head 单一（AC-54/55）。
10. **门禁 exit code 可信度**：正常跑三条请求型脚本记 exit → **故意改坏一条断言**再跑 →
    必须非 0，且根目录 JSON 未被改写（AC-61/62/64）。
