> 1. **正向**：每一条需求，是否都有可执行的测试用例；没有的那条，是「没测」还是「本阶段不测」。

### 0.2 覆盖状态词表（**只允许用这 6 个值**）

| 状态 | 判定（必须同时满足才可标此状态） | 对下游的含义 |
| --- | --- | --- |
| **C 已覆盖** | 有 ≥1 个用例，**断言落在业务量**（件数/金额/台账行数/字段值），且判据可从 `t1` 的坐标或本文档 §2 复现 | 可直接进入回归组合 |
| **P 部分覆盖** | 有用例，但**只断言 HTTP 状态码/200-302**，或只覆盖主干中的一个分支，或断言口径与业务口径不一致 | 可作**烟雾层**使用，**不得**当作业务验收 |
| **W 弱覆盖（口径未锁）** | 用例存在且断言了业务量，但**断言口径仍在文档冲突中**（`t1 §8` 的 X-… 项），或**结论归因于他人实测**（引用须写明取证方） | 必须先锁口径才能进回归 |
| **G 缺口** | 该需求**在本阶段范围内**且有明确测试设计，但**当前无任何用例**（脚本/手工均无） | 见 §6 排序，是最主要的产出 |
| **N 本阶段不测** | 需求已登记，但被规划 `§7.1 明确不做清单` 或 `§7.2 不拍板默认路径` 显式排除 | **登记为已知风险**，不进测试计划 |
| **B 待复核定范围** | 需求真实性/口径**尚未由独立复核确认**（`t1 §7.2 未实测项`），或依赖未拍板项 `Q-1/Q-2/Q-3/Q-4` | 先做 1 次低成本判定，再决定 G/N |

> ⚠ **「有脚本文件」不等于「已覆盖」**：例如 `TC-smoke-test` 覆盖 148 条 GET × 8 身份，但断言只有状态码 ⇒ 对它命中的需求一律标 **P**，不标 C。这是本矩阵与「维护者以为测过了」之间最大的一处认知差。

## 5. 优先级模型（可复核的评分规则）

### 5.1 模型

`优先级 = f(业务破坏力, 覆盖风险, 取证成本, 依赖阻断)`

| 因子 | 取值 | 权重 | 定量化依据 |
| --- | --- | --- | --- |
| **业务破坏力** `I` | 3 = 工资/料账/质量台账数字错，或安全面 | 高 | 需求来源文档的 P0/P1/P2 分级 + `t1 §7.1` 破坏力列 |

| **覆盖风险** `R` | 3 = 零覆盖且需求在范围内（G） | 高 | 本文档 §1 的状态列 |
| | 2 = 弱覆盖 / 口径未锁（W/B）或只断言状态码（P） | | |
| | 1 = 已覆盖（C） | | |
| **取证成本** `C` | 3 = 需新脚本 + 自建夹具 | 中（**成本高不降级业务风险，只决定排队位置**） | `t1 §3.6`（45 张表 0 行）、规划 §3.3 |
| | 2 = 需新脚本或造数 | | |
| | 1 = 现有脚本可扩或纯手工 | | |
| **依赖阻断** `D` | 3 = 不先做，后续批次的验证结论不可信 | 高 | 规划批次顺序（批次3 最先）+ 本矩阵 §8 链 |
| | 2 = 依赖未拍板/未实现 | | |

**定级规则（无例外）**

- **P0**：`I=3 且 R≥2`，或 `D=3`，或（`I≥2 且 R=3 且 C≤2`）。
- **P1**：`I=2 且 R≥2`，或 `I=3 且 R=1`，或 `D=2`。
- **P2**：其余。

**排队规则（同为 P0 时）**：`D 降序 → C 升序`（先做阻断面大、取证便宜的）。
