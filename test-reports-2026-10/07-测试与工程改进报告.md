## 4. 三条硬约束（必须单独成节）

### 4.1 `pending` 死锁 ⇒「先定口径、再接线」（A-32 强制）

**已实测的事实链（t5，本任务复核引用）**：

| 形态 | 实测结果 | 意义 |
| --- | --- | --- |
| `quality_status = NULL` 的新实例真实报工 | `finished_product` **+4**（放行） | 链路本身是通的 |
| `quality_status = 'pending'` 的实例报工 | `finished_product` **+0**，原因可读（静默拒绝） | **门禁已生效**，但无复位路径 |
| 全仓 `quality_status` 赋值点 | **唯一** `routes.py:8899`（人工 PUT） | 自动链路零写点；一旦写入即**永久锁死** |
| 真实库现状 | `production_batch_items` 23 行 `quality_status` **全 NULL**（pending 0） | 死锁尚未在生产数据上发生，但**一次人工 PUT 就能触发** |

**因此修复顺序被硬性约束为**（顺序错就是引入新缺陷）：

```
① DEC-1 口径裁定（业务 + 开发 + 测试三方签字）
      ├─ 取值语义：NULL=未开始/未判定 · pending=质检进行中 · pass=合格 · fail=不合格
      ├─ 复位路径：全部关联任务完成且 pass ⇒ 写 pass；处置(返工/报废/让步)done ⇒ 回到可入库
      └─ 写点归属：自动链路=apply_inspection_result（唯一）；人工 PUT routes.py:8899 保留为纠正通道
② P-03 实现 fail 落地 + pass 回写 + 复位（同一提交内）
③ P-07 把门禁的 pending 判据改成「确有在办质检任务」，并验证自动复位真的发生
④ P-02 补报工路径 NC（与 ② 同函数，建议同批）
```

**验收判定表（必须逐格实测，缺格即不算通过）**：

| `quality_status` | 正常报工（未质检） | 报工后质检 fail | 处置 done 之后 |
| --- | --- | --- | --- |
| NULL（真实库现状） | **必须入库**（实测 +4 ✅） | 应建 NC 并写 fail（当前 **+0** ❌） | 不适用 |
| pending | **必须不锁死**（当前 fg **+0** ❌，修复后须能入库或给出明确复位动作） | 应写 fail | **必须恢复可入库**（AC-15，本轮不可判定） |
| pass | 入库 | 不适用 | 不适用 |
| fail | **必须拒绝**（当前门禁确实拒绝 ✅） | — | 处置完成后按复位口径 |

> **红线**：只写 `fail` 不写 `pass`/不给复位 ⇒ 修好 AC-13/AC-18 却引入 AC-15 的阻塞，属**回归**。P0-2.4（放行）与 P0-2.5（死锁）两条判据必须**成对**常驻。
